1. 总览

1.1 仓库的主实现

主实现是 Rust workspace。codex-cli/bin/codex.js 是 npm 分发入口：识别系统和 CPU，定位对应平台的原生二进制，再启动子进程。它不是 Agent 主循环。实际 CLI 分发器在 codex-rs/cli/src/main.rs。

技术组成可以沿职责阅读：

  • cli：命令解析、入口分发、恢复/分叉/登录等命令。
  • tui：基于 Ratatui 与 Crossterm 的交互终端界面。
  • exec：无交互运行、JSONL 事件输出、结构化最终输出。
  • app-server、app-server-client、app-server-protocol：应用接入、请求分发、事件与审批往返。
  • core：会话、任务、采样循环、上下文与核心执行编排。
  • protocol：内核操作、事件和模型内容结构。
  • tools、ext/*、core-plugins：工具公共契约、能力扩展和插件装配。
  • model-provider、models-manager、login、codex-api：模型后端、目录、认证和通信。
  • exec-server、sandboxing、linux-sandbox、windows-sandbox-rs、network-proxy：执行环境及安全边界。
  • history、rollout、thread-store、state：模型历史、持久化、历史读取和状态索引。
  • sdk/typescript、sdk/python：通过不同协议层复用运行时的客户端。

源码依据：Rust workspace、npm 入口、core 的职责声明、TUI 终端后端。

2. 从启动命令到可工作的客户端

2.1 npm 入口：选择并启动原生程序

codex.js 将 platform + arch 映射成 target triple，例如 Windows x64 对应 x86_64-pc-windows-msvc。之后优先从平台包定位 vendor/.../bin/codex.exe，并保留兼容的 vendor 查找方式。

使用异步 spawn 还有一个实际目的：父进程可以处理和转发终止信号，避免 Ctrl+C 后只结束包装进程。理解启动性能或退出行为时，应该把这一层与 Rust 运行时分开检查。

源码：平台映射与二进制定位、异步启动的设计说明。

2.2 Rust 入口：一个二进制分发多种工作模式

入口先初始化构建信息，再经过 arg0_dispatch_or_else。这允许同一套可执行文件基础设施根据调用名处理特定辅助入口。常规路径进入 cli_main，通过 Clap 解析主参数与子命令。

源码：main 与 cli_main、子命令定义、功能覆盖转换。

2.3 TUI 有三种 app-server 目标

本地源码明确建模三种后端：

  • Embedded：在当前进程启动 app-server runtime，通过内存通道通信。
  • LocalDaemon：连接共享的本地服务。是否允许回退由目标状态明确记录。
  • Remote：连接指定远程端点，工作目录及服务端状态属于远程后端。

--no-daemon 选择 Embedded；显式远程端点及默认 daemon socket 参与其余选择。恢复/分叉已有会话时，代码会保护已选后端，不能把连接失败后回退当成无条件成立的行为。

隐式接入本地 daemon 还要通过兼容性检查，例如 --oss、选定 profile、workload identity、执行器选择及部分配置覆盖会影响是否适用。自动启动另外受 DaemonAutoStart 及启动条件控制，不能只根据本机存在 socket 推断最终后端。

因此，“TUI 使用 app-server”不等于“每次都新起一个 app-server 子进程”，也不等于“所有会话都运行在本地”。

源码：后端枚举、目标选择、连接与回退路径、daemon 排除条件、自动启动条件、CLI 的交互启动。

2.4 无交互 exec 也通过 app-server

codex exec 负责解析输入、选择输出处理器、准备配置，再启动 InProcessAppServerClient，创建或恢复 thread，提交 turn，并消费服务端事件。它是同一内核的另一种客户端。

与 TUI 相比，exec 的重要差异是输入和输出契约：

  • 可以从命令参数或标准输入取得任务。
  • --json 向标准输出发送 JSONL 事件，旧别名 --experimental-json 仍被接受。
  • --output-schema 约束最终回答形状；它与整个事件流的结构是两件事。
  • --output-last-message 可以单独写出最终消息。
  • 非交互客户端必须对服务端请求给出明确处理；不能期待一个并不存在的审批弹窗。

源码：exec run_main、进程内客户端启动、参数定义、服务端请求处理。

3. app-server：将运行时变成可集成的服务

3.1 协议层和内核层的分工

app-server-protocol 定义外部可见请求、响应和通知，例如 thread/start、turn/start、turn/steer、turn/interrupt。protocol 定义更靠近执行内核的操作与事件，如 Op、EventMsg，以及模型输入输出的 ResponseItem。

源码把外部消息称为 JSON-RPC，但明确注明不发送、也不要求 "jsonrpc": "2.0" 字段。自己实现客户端时应遵循这个仓库的 schema，不能只凭通用 JSON-RPC 库的默认行为猜测线格式。参见 RPC envelope 定义。

这两层并非名称不同但内容完全相同的消息集合。app-server 还负责初始化、客户端能力、请求校验、配置与账户接口，以及内核事件到产品事件的映射。前端通常不应绕过这些契约直接操作内部状态。

源码：外部方法登记、内核 Op、内核事件、模型内容项。

3.2 MessageProcessor 是接入层的分发中心

服务端将账户、配置、目录、环境、thread、turn、插件等请求交给不同的 request processor。初始化被特殊处理，普通请求要在连接完成初始化之后进入正常分发。

MessageProcessor 在构造期间装配共享的配置管理、线程管理及各请求处理器。真正的 Agent 执行仍由 core 中的 thread/session/task 承担，而非一个 RPC 处理函数从头到尾同步执行全部工作。

这样，turn/start 的响应可以先返回被接纳的 turn，后续工作通过通知持续送达。拿到请求响应不代表任务已经完成。

源码：MessageProcessor 装配、请求入口、初始化分支、turn/start 分发。

3.3 Thread、Turn、Item 是客户端的核心对象

可以用三个层级理解客户端数据：

  1. Thread：可恢复的对话/工作会话，持有会话身份和相关设置。
  2. Turn：一次工作周期，包含输入和运行状态，也可能接受运行中的追加输入。
  3. Item：轮次中的具体内容或活动，例如用户消息、助手消息、工具执行等。

Turn 状态显式区分 Completed、Interrupted、Failed、InProgress。客户端应检查完成通知中的状态，并消费对应活动项，不能用“收到了最后一段文本”判断成功。

源码：thread/start 参数、TurnStatus、turn/start 输入、完成通知。

3.5 进程内模式保留协议语义

app-server/src/in_process.rs 使用内存通道替代 stdio 或 socket，但继续运行同一 MessageProcessor。请求是 typed ClientRequest，结果仍沿 JSON-RPC result envelope 回传。app-server-client 再提供更高层的异步请求、事件消费和关闭管理。

背压也有明确边界：底层命令队列有界，提交可能返回 WouldBlock；部分通知在饱和时可能丢弃并以 Lagged 反映。审批等服务端请求不能被静默遗弃，否则 Agent 会永久等待。客户端 facade 使用另一层本地事件队列持续排空底层 runtime，避免“等待 RPC 响应时不读通知”造成死锁。不能笼统说整个系统的所有队列都同样有界。

源码：进程内 runtime 的生命周期与背压契约、共享客户端说明、exec 对 Lagged 的处理。

3.6 外部传输和部署边界

独立 app-server 入口支持 stdio://、Unix socket、WebSocket 及 off 等监听形式。协议 schema 和 TypeScript 类型生成也由 CLI 提供命令入口。部署时应分别考虑传输认证、服务端工作目录和工具执行环境；“能连到 app-server”只说明集成通道成立，并不自动说明模型认证、执行环境和项目权限都已就绪。

源码：监听参数与启动入口、CLI app-server 命令定义。

4. 会话、轮次与任务

4.1 先区分 Thread、Session、Turn、Task 和 Step

这一版 Core 已经把运行逻辑拆到 session/、tasks/、state/ 等目录，不能再按照早期版本把所有行为归到一个 codex.rs 文件。理解它的关键是分清五种不同的生命周期。

  • Thread 是向上层暴露的对话对象，有稳定的 ThreadId、历史和启动元数据。
  • Session 是这个 Thread 当前在内存中的运行实例，拥有服务、状态、输入队列和活动轮次。
  • Turn 是一轮被 Core 接纳的工作，以 TurnContext.sub_id 标识；可以包含多次模型请求、工具执行和后续输入。
  • Task 是承载这轮工作的 Tokio 后台任务；普通对话使用 RegularTask，此外有 Review 和 Compact 等类型。
  • Step 是一次模型采样请求所使用的配置与能力快照，明确绑定模型、环境、工具和 MCP 连接。

因此，一条用户消息通常开启一个 Turn，一个 Turn 的 Task 可以驱动多次 Step；模型调用工具之后再次采样，通常仍属于同一个 Turn。

这里的 Task 是 Core 的执行抽象，不等同于桌面产品侧栏中用户看到的“任务/聊天”。这里的 Step 也不是模型输出的一段推理文字。

源码入口：CodexThread、Session、TaskKind 与 RunningTask、StepContext。

4.2 CodexThread 是运行时的双向通道门面

CodexThread 持有 Arc<Session> 与 SessionIo，向宿主提供 submit()、轮次输入接口、事件接收和配置查询等操作。

它把“访问这个聊天”与“具体如何执行一轮模型工作”分开：上层提交操作，下层通过事件报告状态。

SessionIo 更进一步把通信端点从状态本体拆出来，包含操作发送器 tx_sub、事件接收器 rx_event、Agent 状态 watch 接收器，以及可被多个调用者等待的 session-loop 完成 future。

这种拆分有实际生命周期意义：宿主可以等待关闭；所有操作发送器被释放时，接收通道关闭，session loop 仍会执行清理。

submit() 的返回值只是生成的 Submission ID，不代表模型已完成工作。需要结果的轮次输入使用 oneshot reply，但这个 reply 也只回答 Core 的接纳和路由决定。

源码：CodexThread::submit、SessionIo 字段、submit_turn_input。

4.3 Submission loop 处理控制面，Task 执行工作面

创建 Session 后，Core 使用 tokio::spawn 启动 submission_loop。

这个循环通过带优先顺序的 tokio::select! 同时观察运行树关闭信号、操作通道和 mailbox 更新，然后按 Op 分派处理函数。

典型操作包括输入、Interrupt、审批答复、权限答复、用户问题答复、Realtime 控制以及 Shutdown。

普通轮次的耗时工作会被注册成后台 Task。控制循环因此可以继续接收 Interrupt 或审批答复，而不必等模型请求结束。

若显式 Shutdown 没有发生而操作通道先关闭，循环退出后仍然调用 runtime teardown，并关闭 thread persistence；“发送端没了”不会直接跳过清理。

源码：session loop 启动、submission_loop、通道关闭后的清理。

4.4 Session 保存什么，哪些内容属于一轮

Session 保存稳定的运行设施，包括 SessionServices、启用的 features、输入队列、MCP 刷新协调器、Realtime 管理器以及 active_turn。

它的 SessionState 通过异步 Mutex 保护，保存会话配置、ContextManager 历史、速率限制、token 使用记录、上一轮设置、压缩窗口、预热句柄和关闭状态等。

SessionConfiguration 是未来轮次继承的默认配置，覆盖 provider、step settings、环境选择、开发者指令、基础指令、权限配置和动态工具等。

这不是把完整全局配置随意复制到每个工具里。执行所需的状态会在 Turn 和 Step 边界进一步捕获。

ActiveTurn 则包含当前 RunningTask、结束记录阶段使用的 finishing 标记，以及可共享的 TurnState。

TurnState 保存本轮等待中的审批、权限请求、用户输入答复、MCP elicitation 和动态工具回复通道，同时累计本轮工具调用数及分模型 token 使用。

这一设计让等待中的工具可以异步挂起：宿主把回复交回 Core，由对应 oneshot sender 唤醒原来的等待者。

源码：Session 的共享状态、SessionConfiguration、SessionState、TurnState。

4.5 输入接纳与 steering：收到消息不等于另起一轮

turn_input::handle 是 Core 判断输入开始新轮次、加入当前轮次，还是拒绝提交的集中入口。

TurnInputMode 明确区分了几种意图：

  • StartOrSteer：优先把输入交给当前可 steering 的轮次；没有活动轮次时才创建新的 RegularTask。
  • StartIfIdle：只有空闲时才能启动；这也承载一部分自动触发的工作。
  • ContinueIfIdle：在指定前一轮状态成立时继续，只接受内部 ResponseItem 类输入。
  • Steer：要求交给当前轮次，并可携带预期 turn ID，避免输入落到错误的轮次。

输入相关的 thread settings 会先验证，只有输入被接纳后才提交，从而避免一条最终被拒绝的输入悄悄修改会话默认值。

启动选项仅在新 Turn 创建时消费；成功 steering 不会用新建轮次选项替换当前 TurnContext。其持久设置更新供后续轮次继承，活动轮次的显式设置更新另走受限制的接口。

Core 返回 Started、Steered 或 NotSubmitted 时，尚未承诺 prompt hooks、历史保存和采样已经结束。宿主不能把这次应答当成回答完成事件。

自动工作还有额外限制：TurnStartKind::Automatic 不能从 Plan 模式自动开始，也不能通过候选设置自动进入 Plan；用户和恢复路径有不同的接纳规则。

源码：输入契约、路由分派、start_or_steer、自动启动模式限制。

4.6 TurnContext 与 StepContext：一轮身份和一次请求的视图

TurnContext 保存本轮的身份、来源、初始配置、环境、输出 schema、扩展数据、计时状态、终止错误和权限授予等状态。

其中 initial_settings 明确保留接纳时的设置，而 next_step_settings 使用 ArcSwap<ResolvedStepSettings> 存放后续 Step 将读取的设置。

因此，“TurnContext 创建后整轮模型和所有配置绝不变化”已经不符合这一版实现。

执行一条模型请求前，Core 捕获 StepContext：先在约定锁顺序下共同读取设置和环境，再等待 executor/MCP 准备，最后绑定该请求实际使用的工具路由、MCP binding、AGENTS.md 和扩展输入。

同一个 Step 使用这份快照完成 prompt 构造、工具声明和工具调用，避免模型看到的是一种工具清单、执行时却使用另一种环境。

这里的“冻结”主要指捕获的配置与能力视图；权限读取仍结合当前 Session grants 和原始 Turn grants，因此不能把它理解成复制一份永远不会更新的授权数据库。

活动轮次设置更新还有双重防线：准备结束后重新确认同一个 Task 仍在运行，并校验托管策略及旧消费者依赖的安全属性。

模型、effort、summary、service tier 等活动更新受 StepModelSwitching 控制；该 feature 在此快照中为开发中、默认关闭。具备 StepContext 不意味着用户默认就能任意在一轮内切换模型。

源码：TurnContext、捕获 Step 的锁与准备顺序、Step 权限访问、活动设置发布、feature 默认值。

5. Agent 主循环与模型通信

5.1 普通对话不是一次 API 调用

普通工作由 RegularTask::run 承载。它先发出 TurnStarted，让前端尽快看到这一轮已经可见且可中断，再运行轮次启动贡献者和消费启动预热结果。

预热就绪时接过对应 ModelClientSession，不可用则后续创建新的实例，取消则仍尝试保留本轮输入。

然后它调用 run_turn。只要本轮没有终止错误且仍有 pending input，RegularTask 还可以以空的初始输入再进入 run_turn，由共享队列补上新工作。

run_turn 自身又包含多次采样循环；而 run_sampling_request 内还包含网络流错误重试循环。阅读代码时必须区分这三种循环：它们分别解决尾部输入、模型与工具继续执行，以及通信恢复。

5.5 ModelClient 与 ModelClientSession 各自缓存什么

ModelClient 是 Session 级对象。它持有 provider、鉴权入口、HTTP client factory、请求贡献者和传输回退状态。

ModelClientSession 是一轮运行中的流式客户端，缓存 WebSocket 连接、上次请求、上次完整响应和 sticky routing token。

x-codex-turn-state 从服务端响应取得后，在同一客户端轮次的重试和 continuation 中保持不变；不应跨新轮次复用。认证拥有者变化时，相关路由状态也要重新建立。

run_turn 在多次采样和流重试间复用同一个客户端实例。预热实例也通过显式交接进入这里，避免第一次真正采样重复建立已准备好的状态。

普通流路径先检查 provider 的 supports_websockets 及 Session 的禁用状态，适用时优先 WebSocket；否则使用 HTTP Responses，HTTP 路径调用 /responses 并接收事件流。

这个选择不是读取旧的 responses_websockets 开关：旧的两个同名 feature 在当前注册表中已标记 Removed。应以 responses_websocket_enabled() 的实际条件为准。

源码：两个 client 的职责、sticky routing 契约、传输选择、WebSocket 启用条件、旧 feature 状态。

5.6 WebSocket continuation 是有条件的增量提交

Core 不会只因为连接还在，就假定服务端上下文与当前历史一致。

它先要求上一条请求和上一条完整响应都可用、有 response ID，再检查模型、tools、reasoning、service tier、output text 设置等非输入属性没有改变。

还需要确认当前输入以“上次请求输入 + 服务端已输出的完整 items”为前缀。只有这些条件满足，才发送 previous_response_id 和新增输入。

输入缩短、前缀不同、模型变化、工具变化或部分 metadata 变化，都会使它回到完整请求路径，而不是错误地在旧上下文后盲目追加。

因此，WebSocket 复用、增量 continuation 和 prompt cache 是不同机制。前者减少连接开销，第二个减少上下文重发，第三个涉及服务端前缀缓存键，不能混为“模型记得之前内容”。

源码：请求属性比较、增量前缀检查、prepare_websocket_request。

5.7 事件流怎样变成可见文字、工具结果与历史

传输层返回的不是最终字符串，而是 ResponseEvent 流。客户端先组合 response interceptors，再映射 provider 错误、记录推理追踪、补齐 item ID，并保留完成的响应供 continuation 使用。

try_run_sampling_request 消费这个流：OutputItemAdded 建立当前活动项并发 item-start 事件；文本与 reasoning delta 转换为前端增量事件。

OutputItemDone 是完整输出项的处理边界。Core 将它交给 handle_output_item_done，取得工具 future、最后一条 assistant message 和是否需要后续采样等结果。

工具 future 被放入 FuturesOrdered，在流处理结束后统一 drain；所以模型的流式输出和已经分派的工具执行可能在时间上重叠，但下一次采样会等这一批工具结果收齐。

Completed 记录 response ID、token usage、usage metadata 和 end-turn 信息。若流在这之前关闭，Core 将其视为错误，不把 TCP/SSE 结束误判为正常回答完成。

token-count 事件会等 pending tools 处理后再发出，避免在 request_user_input 等工具等待用户时不断发进度事件；已经观察到的 token 用量在取消竞争下也尽量保留。

Plan 模式有单独的 assistant 文本分段与计划项处理；存在 turn-item contributors 时，部分流式展示会被推迟到贡献者处理完成。原始输出项、对话历史和 UI item 因此不是简单的一一转发。

ConcurrentReasoningSummaries 默认关闭；启用且 provider 为 OpenAI 时，摘要走 sequential-cutoff 交付分支，展示主要依据完整 summary done，而不是逐 delta 转发。

源码：客户端流映射与完整响应缓存、流消费入口、完整 item 分派、Completed、工具 drain 与收尾、摘要交付 feature 默认值。

5.8 错误重试、回退与停止边界

run_sampling_request 从 provider 取得 stream_max_retries。当前 provider 默认值为 5，配置值还会被上限 100 约束；这个值属于流重连预算，与 request 层重试设置不同。

只有错误给出可重试延时，才继续进入重试逻辑。ContextWindowExceeded 和用量上限等错误会先返回上层执行相应处理，而不是当作普通断网反复重发。

退避优先遵守服务端 Retry-After deadline；它只影响等待时间，不自动增加有限重试预算。

当前默认开启 UnboundedConnectionRetries。但无限连接重试仅适用于 Sampling 的 ConnectionFailed、非内部 Session、且 provider 不是 Amazon Bedrock 的分支；延时从 5 秒倍增到最多 60 秒。

这解释了为何某些网络断连时会长时间显示重连：它可能走连接恢复策略，不能单凭“重试超过五次”就断言实现违反配置。

有限流重试耗尽后，如果还可以从 WebSocket 回退 HTTP，Core 发 warning、重置该重试计数，并切到 HTTPS。

这个回退状态保存在 Session 级 ModelClient，后续轮次也继续走 HTTP；不是下一次采样马上重新探测 WebSocket。无法回退且预算耗尽时，错误才最终向上返回。

源码：provider 重试默认值、有效流预算、错误重试与等待策略、Session 级 HTTP 回退、连接重试 feature 默认值。

5.9 Interrupt、steering preemption 与 mailbox 是三类信号

显式 Interrupt 通过 handlers::interrupt 进入 Task 终止流程。Core 先取消任务 token，等待任务主动退出，超过 100 ms 的优雅退出窗口后再 abort Tokio handle，并调用任务的 abort 清理函数。

若为用户中断且 CodeModeInterrupt 开启，还会中断活动 code-mode cells；这个 feature 在此快照默认开启。

中断标记、hook 和 TurnAborted 事件有专门保存顺序。例如中断历史标记先 flush，再通知客户端，避免客户端收到终止事件后立即重读历史却看不到该标记。

steering 的 preempt 则通常只让当前采样尽快让路，返回 needs_follow_up，在同一 Turn 内消费新输入。它不等于用户要求终止整轮工作。

若当前流支持 interrupt，Core 可请求 Drain，继续收尾已完成 items 与响应状态，随后再发包含新输入的请求；这样下一次 continuation 才有一致的历史基础。

mailbox 更新也可以触发让路。默认 DeferMailboxPreemption 关闭时，在 commentary、partial answer 或 reasoning 的完整 item 边界看到 pending mail，可以结束或 drain 当前响应，并安排 follow-up。

终结回答会尝试把 mailbox phase 从 CurrentTurn 切到 NextTurn，晚来的消息保留给下一轮；已有显式同轮输入时会保留当前接纳，后续显式同轮工作也可以重新打开接纳。

空闲 mailbox 自动唤醒另受 WakeOnAgentMessages 控制，该 feature 默认关闭；显式 trigger-turn 消息或 outstanding durable sleep 还有自己的调度路径。

这些区别决定了事件语义：用户继续补充要求可以延长当前 Turn；用户停止会结束当前 Task；晚来的 Agent 消息则可能排队等下一轮。

源码：Interrupt 入口、取消与 100 ms 窗口、窗口常量、采样 preempt 与 Drain、mailbox 抢占边界、mailbox phase 条件、mailbox feature 默认值、CodeModeInterrupt 默认值。

5.10 阅读和验证这部分实现时的抓手

定位“为什么一条消息没有开始新轮次”，先查 turn_input.rs 的接纳结果，而不是直接追模型 API。

定位“为什么工具执行后又调用了一次模型”，查 needs_follow_up、pending input 和服务端 end_turn。

定位“为什么配置更新没有影响正在流出的回答”，查更新是否只是 thread settings，以及新的 Step 是否已经捕获；已经捕获的 Step 不会被后续配置写入偷偷改造。

定位“为什么换成 HTTP 了”，查 responses_retry.rs 与 Session 级 fallback 状态；定位“为什么没有增量发送”，查请求属性比较与输入前缀验证。

定位“为什么界面显示完成但记录有错误”，检查终止事件内的 error 与生命周期路径，而不只看事件类型名称。

仓库已有针对重试 deadline、输入接纳、模型切换统计、取消及流处理的测试；这些可作为理解语义的第二份证据。本次文档分析只做静态阅读，不把“找到测试”表述成“已经运行并通过测试”。

测试入口：retry deadline 测试、turn input 测试、完成指标与模型切换测试、预热等待时中断测试、流丢弃的取消记录测试。

6. 上下文与提示词工程

6.1 从“拼接 prompt”到“管理世界状态”

这个版本的 Codex 把提示词视为运行时状态的投影。工作目录、执行环境、权限、模型、可用工具、项目说明、插件和协作模式，都有具体的宿主状态；模型看到的是这些状态经过渲染后的消息。这样，模型请求与实际可执行能力才能对应起来。

核心有三个层次：

  • TurnContext 保存一次 turn 的身份、来源、初始设置和权限上下文；可变的后续 step 设置走受控发布路径，不能把它理解为整轮所有配置永久冻结。
  • StepContext 固定一次采样请求实际使用的模型设置、环境、MCP 绑定和工具路由。
  • WorldState 把需要告知模型的状态拆成独立 section，支持全量渲染和相对上次快照的差量渲染。

这一区分很实用：一次用户 turn 内可能经历多轮“模型 → 工具 → 模型”，设置或环境也可能发生变化。把工具声明和执行路由绑定到同一个 StepContext，可以减少“模型看到旧工具，却调用新连接”的状态错配。

源码入口：StepContext、构建 WorldState、WorldState。

6.3 AGENTS.md 的发现规则

agents_md.rs 不会递归读取整个仓库。它从当前工作目录向上寻找项目根标记，再收集“项目根 → 当前目录”这一条路径上的说明文件。

根标记由 project_root_markers 控制，未设置时使用默认的 .git；找不到根时只检查当前目录。空标记列表会关闭向父目录的遍历。

每一级目录只选择一个候选文件，优先顺序是：

  1. AGENTS.override.md。
  2. AGENTS.md。
  3. 配置中的 project_doc_fallback_filenames，按顺序尝试。

因此，同一目录的 override 与普通文件不会全部叠加。多个层级的说明则按从根到当前目录的顺序拼接，让更具体的目录说明出现在后面。

project_doc_max_bytes 是所有环境共同消耗的读取预算。内容过长时按剩余字节截断，而不是无限加入提示词。路径发现也通过执行环境提供的文件系统进行；远程环境的项目说明不必通过本地文件系统读取。

安全边界同样在这条读取链上：不受信任的项目跳过项目说明；受限文件系统读取会携带 sandbox context；fallback 必须是文件名，路径分隔符、空字符，以及 Windows 上的盘符或网络路径语法会被排除。

这意味着 AGENTS.md 是一种受配置和信任状态约束的提示词来源，不能把它理解为绕开权限系统的特殊配置文件。

源码：发现算法和根标记、加载与信任检查、候选文件名过滤。

6.4 全局、线程和仓库说明如何汇合

AgentsMdManager 将全局用户说明、线程说明、项目文件，以及可选的动态 provider 汇成一个已验证快照。它用 semaphore 串行化 refresh，但不会在调用 provider 时持有状态锁，避免外部读取阻塞整个状态访问。

缓存键包括环境选择和项目 trust level。环境或信任发生变化时，管理器先清空旧项目缓存，防止权限收紧后仍把已不可访问的说明保留在模型上下文中。

刷新成功且大小验证通过之后，新指令才会替换已应用快照。某些隔离 reviewer 可以固定项目快照，Some(empty) 也具有含义：使用明确的空快照，并跳过新的执行器发现。

一个容易误读的细节是：该实现并非每次采样都重新扫描磁盘上的 AGENTS.md。环境和 trust 未变时会使用缓存；动态 provider 则拥有自己的获取和缓存责任。不能据此承诺“编辑项目说明后，下一次模型采样必然重新读取”。

源码：AgentsMdManager、刷新与缓存失效、继承说明。

6.5 WorldState 的 section 与差量

WorldState 用有序 map 保存 section。每个 section 负责自己的状态快照、渲染逻辑、旧格式识别，以及是否应持久化。框架把 section 的具体类型擦除后统一处理，扩展也可以提交自己的 section。

当前内置 section 覆盖模型说明、上下文窗口提示、实时状态、AGENTS.md、权限、协作模式、持久执行、执行环境、Apps/插件说明、延迟工具目录和多 Agent 提示等。

它们不是无条件全开启。例如：

  • 权限提示由 include_permissions_instructions 决定采用详细或紧凑版本。
  • 环境和日期受 include_environment_context、include_environment_context_time 控制。
  • Apps 提示要求 Apps 可用、配置允许，且对应模型允许加入 Apps 用法。
  • 延迟工具的状态提示要求 DeferredToolWorldState。
  • 增量工具声明要求模型使用 Responses Lite，且 IncrementalTools 开启。
  • 模型目录提示还要求存在可见的模型覆盖能力，并开启 ModelCatalogInContext。

差量不是简单比较一大段字符串。WorldStateSnapshot 按 section 保存基线，每个 section 可以根据 Absent、Unknown、Known 三种前态生成更新；恢复旧历史时，“从未有过状态”与“存在但无法解释旧快照”可以区别处理。

源码：section 协议、全量与差量渲染、实际 section 组装、增量工具门控。

6.6 初始上下文的消息角色与顺序

build_initial_context_with_world_state 汇合内置 world state 和扩展提交的 thread/turn 上下文，并保留 developer、上下文型 user 消息与独立 item 的边界。

模型切换说明被放到 developer 上下文的前面；多 Agent 使用提示和当前模式有明确顺序；Guardian policy 在特定内部会话中保持独立 developer 消息；managed developer instructions 也有独立的后置处理。

这体现了一个重要实现原则：提示词不只是内容，角色、位置和来源也参与语义。把它们压成一个大字符串会丢失模式覆盖、审计和恢复需要的信息。

扩展通过 PromptSlot::ContextWindow、DeveloperPolicy、DeveloperCapabilities 申明放置位置。框架决定怎样与核心上下文合并，插件无需直接修改主循环内部的消息数组。

源码：初始上下文组装、角色与 placement 处理、记录上下文更新。

7. 压缩、持久化与恢复

7.1 模型窗口与完整历史是两个对象

ContextManager 保存当前模型窗口，RolloutItem 历史承担持久化与重放。两者有关联，但不是同一个可无限增长的数组。

ContextManager 内部使用 Arc<Vec<ResponseItemEnvelope>>，使只读快照共享历史；需要修改时才复制。它还单独维护 retained context、review history、token usage、历史版本、用户输入 revision、上次 TurnContextItem 和 world state baseline。

因此，压缩当前模型窗口不等于删除磁盘上的完整会话记录。窗口内容可以替换为摘要或服务端 compaction item，rollout 仍记录发生过的替换与恢复元数据。

ResponseItemEnvelope 也使模型内容与宿主元数据分离，例如工具归属、压缩模型标记和来源信息可以附着在 item 上，而不一定作为提示词正文送给模型。

源码：ContextManager 状态、RolloutItem、CompactedItem。

7.2 什么时候触发压缩

上下文窗口计数同时考虑两条限制：模型完整窗口是硬上限；自动压缩额度可以按全部上下文，或按初始 prefix 之后新增的 body 计算。

AutoCompactTokenLimitScope::Total 使用当前活动上下文；BodyAfterPrefix 以窗口首轮 prefill 为基准扣减。完整窗口限制独立存在，不能通过调小统计范围绕过。

配置还允许在 turn 结束时按窗口百分比提前压缩。启用 TokenBudget 时，可以保留 fallback buffer，但只有实际配置了相应 fallback prompt 才保留这部分缓冲。

这些统计依赖模型返回的 usage 和本地估算等运行时信息；“剩余上下文”是 harness 的预算判断，不是对服务端 tokenizer 的绝对承诺。

源码：窗口与阈值计算、自动压缩限制与硬上限。

7.3 三种压缩路径要分开看

手动 compact task 会先捕获 step，再构建新窗口所需的 world state，然后根据配置和 provider 能力选择实现：

  1. TokenBudget 开启时，进入专门的 token-budget 压缩路径。
  2. provider 声明 RemoteCompactionSupport::V2 时，走远程 V2 压缩。
  3. provider 不支持该能力时，使用普通 Responses 调用生成摘要。

普通 Responses 摘要路径使用 compact_prompt 或内置 summarization prompt。它仍然要调用模型；这里所谓“local”是客户端负责摘要协议与安装过程，不代表本机运行了一个离线摘要模型。

RemoteCompactionV2 在 feature 表中已经标记为 Removed，不能把它当成目前选择远程压缩的主要开关。当前 task 直接读取 provider capabilities。

压缩前后可触发 PreCompact、PostCompact Hooks。停止结果会传播为 turn aborted，而不是继续使用一个看起来成功但生命周期未完成的压缩流程。

源码：手动任务分流、普通摘要路径、压缩 Hooks、已移除标志。

7.4 异步压缩不是默认行为

后台压缩先抓取某个历史 prefix，在前台继续执行时请求压缩结果。安装时把压缩后的 prefix 与尚未压缩的 live suffix 拼回去。

它必须同时满足 AsyncCompaction 开启、TokenBudget 关闭、provider 支持远程 V2。该 feature 在当前提交的默认值是 false，且属于 UnderDevelopment。

后台启动还受比例阈值、取消状态、shutdown 状态、同一输入是否已尝试、认证 owner generation 等条件约束。前台还未建立服务端模型 pin 的 pre-turn 阶段，也不会立刻启动并行请求。

7.5 压缩 checkpoint 保存了什么

CompactedItem 不只是摘要字符串。安装时还保存 replacement history、retained context、Guardian checkpoint、MCP resource origins、窗口编号与 UUID、压缩 response ID、最新 usage，以及恢复多 Agent/turn 状态所需的 metadata。

随后把 Compacted、完整 WorldState、冻结的 TurnContext 和当前设置事件一起写入 rollout，使后续恢复能够知道“这个摘要是在哪个状态下形成的”。

并发目标变更也被照顾：完整替换会保留压缩输入快照之后接受的 goal updates；prefix 替换保留 live suffix 中的状态更新。否则，用户在摘要生成期间修改目标，可能被旧快照覆盖。

源码：压缩替换及 goal updates 保留、checkpoint 与恢复字段、checkpoint 持久化。

7.6 ThreadStore 是存储抽象边界

core/session 使用 LiveThread，后者依赖 ThreadStore trait。具体后端可以是本地存储、内存实现，或仓库之外提供的其他实现。

职责分层如下：

  • Session 决定哪些运行时事实需要记录。
  • LiveThread 组织活动线程的持久化生命周期，并观察已追加内容形成 metadata patch。
  • ThreadStore::append_items 追加 canonical history，不从内容中自行推导业务 metadata。
  • 显式 metadata API 写入标题、状态、项目和其他索引字段。
  • LocalThreadStore 管理本地 rollout 与 SQLite 索引。
  • RolloutRecorder 负责实际 JSONL 写入和 writer 生命周期。

需要注意 README 与当前实现的一个细节差异：README 用 update_thread_metadata 概括 metadata 写入；当前 LiveThread::append_items 的历史观察结果走 record_thread_metadata，显式更新另有 API。阅读时应以 trait 和调用点为准。

源码：ThreadStore trait、LiveThread、追加与 metadata 观察、RolloutRecorder。

7.7 JSONL、数据库与压缩存储

本地 rollout 是可检查和重放的 JSONL 数据流；SQLite 提供可查询 metadata、队列、日志、目标、记忆以及分页历史等能力。

当前文件布局将不同职责拆到不同数据库：state_5.sqlite、logs_2.sqlite、goals_1.sqlite、memories_1.sqlite、memories_v2_1.sqlite、queue_1.sqlite 和 thread_history_1.sqlite。这些名字属于当前提交的实现细节，版本迁移可能改变它们。

不能把所有 SQLite 文件都当成随时可删的缓存。标题索引、goal 状态、待处理项和记忆作业的租约等，有各自的持久化语义；历史 JSONL 也不一定包含所有外部状态。

本地线程存储还有分页、压缩和 migration 管线。local_thread_store_compression 与 background_paginated_rollout_migration 在该提交默认关闭；仓库中出现压缩 reader/writer，不表示所有运行环境已使用这种格式。

源码：数据库划分、StateRuntime、本地 ThreadStore、压缩与迁移标志。

7.8 Resume 是结构化重放

reconstruct_history_from_rollout 不会把每行日志直接照搬成下一次模型输入。它要恢复模型窗口、retained facts、review history、最后 turn、设置 baseline、world state 和窗口编号。

重放会寻找最新的可用 compaction checkpoint，再应用其后缀。只有 checkpoint 包含 replacement history、窗口编号，并满足相应 resume contract 时，才能安全限制重放范围；不完整的新 checkpoint 不能随意退回旧 checkpoint 截断历史。

rollback、fork 和压缩会改变哪些 segment 仍然有效。代码以 turn segment 处理这些关系，并区分“从未设置 reference context”和“此前 baseline 已被压缩清除”，避免错误地继续做增量 diff。

这也是恢复能力不能仅靠 UI 历史文本实现的原因：界面展示、模型输入、持久化记录和运行时 checkpoint 是相互关联的不同视图。

源码：恢复结果结构、checkpoint 选择、WorldState 恢复。

8. 工具系统与调度

工具系统把模型产生的结构化请求转换为有生命周期、可取消、带权限上下文的实际操作。这里的“工具”包含终端、补丁、MCP、客户端动态工具和扩展提供的工具，但它们并不全部在同一个位置执行。
本地工具由 Core 路由到运行时；部分托管工具只把规格交给模型服务，例如模型服务端执行的搜索。
因此，阅读工具架构时需要分别追踪“向模型公布什么”和“谁负责执行什么”。

实现入口是 spec_plan.rs:133、router.rs:85 和 registry.rs:406。

8.1 工具契约：规格与可执行对象绑定

共享 crate codex-tools 定义 ToolExecutor<Invocation>。执行器同时提供工具身份 tool_name()、模型可见规格 spec() 和处理入口 handle()。
它还声明默认曝光方式、发现元数据、并行能力，以及参数指向哪些执行环境。
这个接口避免把一个工具的 schema 和执行函数维护成两张容易错位的表。

Core 再用 CoreToolRuntime 补充宿主相关行为：参数类型匹配、环境解析、Hook 输入、取消策略、工具生命周期和缓存规格。
ToolInvocation 则携带本次调用的 Session、StepContext、取消令牌、调用 ID、参数、来源和环境。
StepContext 很关键：异步工具应使用“当时公布该工具的采样步骤”的设置，而不是随意读取后续步骤的新设置。

参见 tool_executor.rs:106、registry.rs:63、context.rs:112。

ToolName 保留 namespace 与 name，路由时不把二者过早拼接成字符串。
只有跨越旧 Hook、遥测或历史兼容接口时，才通过 flat_tool_name() 展平。工具参数也有明确类型：普通 function arguments、freeform/custom input、MCP 等分别走对应分支。
不知道工具名称属于可反馈给模型的调用错误；注册工具收到不兼容的 payload 则可能成为 Fatal，因为它表示内部契约被破坏。

参见 tools/mod.rs:47、router.rs:257、registry.rs:728。

8.2 每个步骤重新形成可用工具计划

build_tool_router() 先创建带 ToolPolicy 的 registry，再合并多种工具来源：

  1. Core 内建工具，例如 exec_command、write_stdin、apply_patch、计划和协作工具。
  2. 当前 MCP binding 提供的 MCP/App 工具。
  3. 扩展贡献者按当前 step 提供的工具执行器。
  4. 客户端在 thread/turn 上声明的动态工具。
  5. 只需向模型服务公布的 hosted tool specs。

随后 finalize_tool_router() 统一处理曝光、搜索、Code Mode 包装、名称冲突和模型最终可见规格。模型能力、feature flags、所选环境、工具策略都会影响这个结果。
所以磁盘上存在一个工具实现，并不意味着当前会话一定向模型提供它。

参见 spec_plan.rs:133、spec_plan.rs:359、spec_plan.rs:1185。

ToolPolicy 的允许名单在注册时就生效。
外部工具不能占用默认 namespace 下保留的 exec_command、shell_command 名称；重复外部工具会被跳过并记录冲突。若启用 error_on_tool_collisions，最终计划会把工具名、namespace 所属或 description 冲突转成明确错误。
这既减少模型工具目录歧义，也避免一个外部工具意外替换终端执行入口。

参见 registry.rs:498、registry.rs:539、spec_plan.rs:473。

8.3 曝光方式决定模型如何找到工具

该版本不只有“显示/隐藏”两个状态。
ToolExposure 包括 Direct、Deferred、DirectModelOnly、DeferredModelOnly、CodeModeOnly、Hidden。
它们分别控制初始模型工具表、工具搜索和嵌套 Code Mode 三种表面。例如 Deferred 工具可先不占用初始完整 schema，模型通过工具搜索获得发现信息后再调用。
DirectModelOnly 则保留模型直接调用能力，同时排除嵌套 JavaScript 调用。

曝光状态主要是目录和调用表面的控制；它不等同于操作系统权限。尤其 Hidden 的定义是保留注册和分发能力、不给模型曝光，而不是删除执行器。
真正禁止某工具进入当前工具计划，应查看 ToolPolicy、来源启用条件和注册过滤。
真正限制文件或网络副作用，则继续查看审批与沙箱链路。

Code Mode 工具名会经过标准化和去重。
CodeModeOnlyStrictThirdPartyTools 开启时，符合条件的第三方工具会保持从 exec 内发现的路径，相关 omit 配置不能悄悄把它们全部抹掉。

8.6 Hook 的位置与边界

PreToolUse 可以阻止调用，也可以更新输入；更新后的输入要重新按工具契约解析。
例如补丁 Hook 不能偷偷改变已经选定的 environment。
PostToolUse 在操作完成后运行，可以追加上下文、替换模型可见反馈，或拒绝把结果交给模型。
但源码明确说明：PostToolUse block 拒绝的是结果，已经完成的工具执行不会因此撤销。

这使 Hook 适合做组织规则、输入修正、结果反馈和审计接入，但它本身不替代内核沙箱。
参见 registry.rs:806、registry.rs:931、apply_patch.rs:418。

9. 命令、补丁与 Code Mode

终端工具、结构化补丁和 JavaScript 编排覆盖三种不同工作：运行现有程序、精确修改文本、组合多个工具结果。三者共享 harness 的路由、上下文和生命周期机制，但实际执行后端不同。
特别要区分 exec_command 与 Code Mode 的 exec：前者启动 shell 命令，后者执行受限 JavaScript，并通过回调调用其他工具；部分客户端表面会显示为 functions.exec。

9.1 exec_command：一次调用可以留下持续进程

ExecCommandHandler 先选择执行环境，再解析 cwd、shell、login、TTY、yield 时间、输出预算和权限参数。
远程环境使用远端报告的 shell；请求另一个不受支持的 shell 类型会被拒绝。本地沙箱需要原生路径时，会检查 PathUri 的路径惯例，避免把 Windows 盘符路径误解释为 POSIX 路径。

参见 exec_command.rs:177。

处理器把请求交给 session 级 UnifiedExecProcessManager。管理器负责进程 ID、会话表、输出收集、保留后台终端、终止和资源回收。
底层既可以是本地 PTY/pipe 进程，也可以是 exec-server 进程，但模型看到的是统一的终端控制接口。
命令短时间内结束时直接返回退出码；仍在运行时返回 session ID，后续可由 write_stdin 继续读取输出或输入字符。

参见 unified_exec/mod.rs:1、process_manager.rs:520、process_manager.rs:1359。

yield_time_ms 表示当前工具调用愿意等待多久，并不天然等于进程最大寿命。
统一执行还包含 completion-only/one-shot 路径，后者在超时或取消后结束进程，不暴露可继续写入的终端权限。当受管理配置关闭 UnifiedExec 时，工具计划可以保留 one-shot exec_command，但不提供 write_stdin；若策略要求必须统一执行，则直接不注册 shell 工具。

参见 spec_plan.rs:1242、oneshot.rs:1。

输出采用有界缓冲与截断，不能把终端当成无限日志存储。此提交的常量包括 1 MiB 的统一执行输出上限、默认 10,000 output tokens 和最多 64 个保留进程。
HeadTailBuffer 保留稳定的开头与最新末尾，并记录中间丢弃字节数；这样模型仍可看到启动信息和最近错误。
这些是当前实现参数，客户端或配置约束也可能进一步收紧等待时间。

参见 unified_exec/mod.rs:75、head_tail_buffer.rs:5、process_manager.rs:1768。

9.2 write_stdin 还需要管理“终端保留的权限”

空字符串写入通常是轮询输出，非空输入会进入已经运行的进程。终端启动时保存权限、网络状态、environment、cwd 和是否提权等信息。
后续输入不能只检查当前 turn 的权限，因为终端可能仍保留旧的更宽权限。
stdin_approval 因此比较启动策略与当前策略，必要时为输入重新请求审批。

参见 write_stdin.rs:78、stdin_approval.rs:120。

一个特别重要的拒绝分支是：当前策略新增了禁止读取路径，但旧终端在无沙箱状态启动，或者仍使用不同的文件系统上下文。审批无法给已经运行的进程补装读取限制，所以实现要求新建终端。
空轮询、特定非 TTY 中断输入等有显式免审分支；严格自动审查下，普通非空输入也可能继续审查。
这比“批准一次终端，之后随意输入”更细。

参见 stdin_approval.rs:126、stdin_approval.rs:191。

write_stdin 不再次发同一条 Bash PreToolUse，因为它是已有会话的传输操作。
当一次轮询读到了原命令的最终退出结果时，它可以补发原命令配对的 Bash PostToolUse。这解释了为什么工具调用数、终端进程数和 Hook 触发数不是简单的一一对应。

参见 write_stdin.rs:155。

9.3 apply_patch：先理解改动，再执行文件操作

补丁工具接受 freeform patch，不是把整段输入交给 shell。
codex-apply-patch 解析 Add/Delete/Update/Move hunks，读取原文并验证替换上下文，形成 ApplyPatchAction。
Action 保留原始 patch、绝对 PathUri 和结构化文件变更，供审批、diff、事件与实际执行共同使用。遇到解析错误、上下文不匹配或隐式补丁输入，会给模型明确失败，而不是猜测执行。

参见 apply-patch/src/lib.rs:144、handlers/apply_patch.rs:304。

assess_patch_safety() 检查所有写入目标，移动还要检查目标路径。
只写允许目录且存在对应沙箱能力时，可自动批准；越界则根据 approval policy 请求审批或拒绝。即使字符串路径看似在工作区内，执行仍要保留沙箱，因为硬链接、符号链接等不能只靠表面路径判定。
Disabled/External profile 则显式表示由本层不装外层沙箱，不能误写成仍受同等隔离。

参见 safety.rs:67、safety.rs:146。

执行通过 ApplyPatchRuntime 与所选环境的 ExecutorFileSystem 完成，传入明确的 FileSystemSandboxContext。它不要求“修改文件必须在当前控制器机器上”；远端工作区也使用同一套补丁语义。
若原本需要的沙箱被绕过，follow_symlinks 会进一步收紧。
补丁还会加入 turn diff tracker，并通过 begin/end 与可选 streaming events 更新界面。

参见 handlers/apply_patch.rs:504、runtimes/apply_patch.rs:184。

这里没有“多文件补丁永远原子提交”的保证。运行时维护 committed_delta，即使后续文件失败，也记录之前已经提交的变更。
调用方可以据此报告真实修改，重试和中断也应尊重这个事实。
intercept_apply_patch() 还识别终端请求中可解析的 apply_patch 调用，把它转入同一条结构化补丁流程。

参见 runtimes/apply_patch.rs:217、handlers/apply_patch.rs:463。

10. 权限、审批与操作系统沙箱

Codex 把动作策略、审批决策和实际隔离分成不同机制。命令被允许，表示当前策略或审批接受这个动作；沙箱负责在动作执行期间约束它能读写哪里、能否联网。
自动审查器可判断动作是否获得授权，但它不会凭判断给进程自动安装内核限制。
理解这一分层，才能解释为什么“已批准”仍可能沙箱失败，以及为什么 Never 不表示拥有完整机器权限。

10.1 运行时权限的事实来源是 PermissionProfile

面向配置的 SandboxMode 保留 ReadOnly、WorkspaceWrite、DangerFullAccess 三个常见名称。运行时更精确的 PermissionProfile 分为：Managed 由 Codex 构建隔离；Disabled 不施加外层沙箱；External 由外部调用者提供文件隔离。
Managed 内含文件系统规则和独立的网络策略，可表示读取、写入、禁止读取及工作区根等更细范围。
Named profile 的显示身份另存 sidecar，不应靠名称反推实际权限。

参见 config_types.rs:104、models.rs:426。

工具还可以声明本次权限意图 SandboxPermissions：使用默认权限、申请附加权限或要求提权。这是请求，不是成功授权；它要经配置、参数校验、execpolicy、审批与沙箱转换。
多个执行环境各自拥有权限上下文，工作区根保持符号/URI，直到实际 executor 才转换为本机路径。

参见 models.rs:66、orchestrator.rs:146。

10.2 execpolicy：在执行前判断具体命令

ExecPolicyManager 加载规则，对解析后的命令片段执行多命令检查，得出 Allow、Prompt 或 Forbidden。
它结合显式规则、命令来源、平台和未匹配命令的启发式策略。Prompt 还必须服从 approval policy：例如 Never 不能继续弹出审批，Granular 可分别禁止规则审批和沙箱审批。
最终得到 ExecApprovalRequirement::{Skip, NeedsApproval, Forbidden}，供统一 orchestrator 消费。

参见 exec_policy.rs:321、exec_policy.rs:350。

这里还有一个容易忽视的行为：只有所有解析命令片段都被显式 Allow 规则覆盖，才设置 bypass_sandbox=true。普通启发式 Allow 不等于显式授予相同的信任。
模型不支持 prefix rules 时，可复用规则修订也会收紧；用户选择保存的规则还需走 amendment 校验和持久化。
execpolicy 分析的是命令及规则，不能把它当成对任意脚本实际运行行为的完整静态证明。

参见 exec_policy.rs:362、exec_policy.rs:445、exec_policy.rs:469。

10.3 审批政策与审批人是两条配置轴

AskForApproval 包括 untrusted/UnlessTrusted、OnRequest、Granular 和 Never。
它控制哪些动作可以进入审批流程；旧 on-failure 在本提交中是 OnRequest 的兼容别名，不是另一个独立枚举。
ApprovalsReviewer 则选择 User 或 AutoReview；guardian_subagent 是 AutoReview 的旧别名。
Granular 进一步划分 sandbox、rules、skill、request_permissions、MCP elicitations 等审批类别。

参见 protocol.rs:1097、config_types.rs:183。

Session::request_approval() 的优先级是 PermissionRequest hooks，然后 Guardian 或用户。
动作统一表示为 ApprovalAction，涵盖命令、终端输入、补丁、MCP 调用、网络和权限请求。命令缓存键包含 environment、规范化命令、cwd、TTY、sandbox permissions 和 additional permissions；补丁按 environment 与路径建键。
缓存不能只靠 tool call ID 或命令文字匹配，否则不同机器或更宽权限可能误用旧批准。

参见 approvals.rs:70、approvals.rs:236、approvals.rs:466。

10.4 Guardian：受限审查者与宿主强制执行协作

Guardian 收到的是绑定到具体动作的审查请求，并保留发起步骤的模型、审批设置、环境和项目指令。Core 强制管理要求和取消条件；reviewer 扩展负责路由、证据和审查过程。
默认自动路由条件是 OnRequest/Granular 配合 AutoReview；管理要求或特定模型要求还可能强制审查。
没有自动决策贡献者不表示默许：路由可回到用户流程，必须 Guardian 时则进入同步审查。

参见 guardian/mod.rs:87、guardian/decision.rs:46、routing.rs:55。

同步 reviewer 有受宿主强制的工具白名单：exec_command、write_stdin、view_image、exec、wait。它要求 Managed sandbox 和 UnifiedExec，不暴露附加权限字段；继承环境与权限会求交到只读上限，review turn 使用 Never。
这允许审查者检查证据，同时降低“审查者自己执行待审写操作”的权限。
它仍是模型辅助判断，最终批准/拒绝要由宿主绑定到动作后执行。

参见 settings.rs:43、settings.rs:60。

Guardian V2 的异步/快速决策与同步 reviewer 分开演进。路由在重试、提权、模型要求新审查等情况下设置 require_fresh_review，即使扩展给出 Allow，也不能一律沿用旧批准。
本提交 guardian_approval 默认开启、guardianv2 默认关闭；这描述代码默认，具体启用还受模式、模型和管理要求影响。

参见 routing.rs:119、features/src/lib.rs:1902。

10.5 ToolOrchestrator 把审批和执行尝试接起来

flowchart TD
    A[命令或补丁请求] --> B[形成审批要求]
    B --> C{Forbidden / NeedsApproval / Skip}
    C -->|Forbidden| X[返回拒绝]
    C -->|NeedsApproval| D["Hook → Guardian 或 User"]
    C -->|Skip| E[选择初次执行权限]
    D -->|批准| E
    D -->|拒绝/中断| X
    E --> F[选择本机或 executor 沙箱]
    F --> G[运行第一次 attempt]
    G -->|成功或普通失败| H[返回真实结果]
    G -->|识别为 Sandbox Denied| I{政策是否允许重试}
    I -->|否| X
    I -->|是| J[按实际重试权限重新审批]
    J --> K[保留必要限制后第二次 attempt]
    K --> H

核心入口 run() 先处理审批要求，再选择初始沙箱并运行。只有特定 SandboxErr::Denied 分支才考虑重试；程序本身报错、测试失败或一般 I/O 错误不会统一被当作沙箱拒绝。
重试还要看工具是否允许升级、approval policy、网络拒绝类型和能否安全无沙箱执行。
StrictAutoReview 下，即使上游给出 Skip，动作也可能被送入严格审查。

参见 orchestrator.rs:125、orchestrator.rs:388。

初次 Guardian 批准仅覆盖它审查过的权限；沙箱失败后准备更宽权限的重试，不能直接把这次批准视作通行证。代码区分 User/Hook 与 Guardian 的批准来源，并在需要时把 retry action 更新为真实的 RequireEscalated 权限后再审。
这说明审批对象应是“动作 + 权限 + 环境”，而不是一句抽象的“允许运行这条命令”。

10.7 OS 隔离后端：同一权限意图，不同平台机制

SandboxManager 根据权限、工具偏好、网络要求和平台选择后端，再把请求转换为真正的命令启动参数。
SandboxType 包括 None、MacosSeatbelt、LinuxSeccomp、WindowsRestrictedToken、WindowsMxc。
这里的类型名是历史稳定接口，不能只看 LinuxSeccomp 就认定 Linux 没有文件系统隔离。

参见 manager.rs:313、sandbox.rs:29。

Linux。 当前文件系统受限的默认 pipeline 使用 bubblewrap 构建受限文件视图，再在内部阶段施加 no_new_privs + seccomp。分成两阶段是为了让 bubblewrap 先完成可能依赖特权的隔离设置，再收紧系统调用。
完整磁盘写权限且没有托管代理要求时，helper 可走仅进程内限制的快速分支；这时无需为文件写隔离启动 bubblewrap。
默认 bubblewrap 路径失败不会静默降级到 legacy Landlock。源码仍保留已弃用的 use_legacy_landlock 开关和 Landlock 安装实现，但当前 helper 会先拒绝“legacy mode + 文件系统受限”的请求；托管代理还会抑制该 legacy 参数。
core/README.md 仍描述旧的“legacy sandbox-equivalent 配置可走 Landlock”行为，与此提交的 helper/安装函数注释不一致，本文按实际执行分支说明，并不把保留实现描述成已删除。WSL1 对需要 bubblewrap 的请求也有不支持分支。

参见 core/README.md:40、linux_run_main.rs:249、linux_run_main.rs:263、linux_run_main.rs:380、seccomp.rs:147、landlock.rs:53、manager.rs:802。

macOS。 Seatbelt 通过生成的策略与固定 /usr/bin/sandbox-exec 启动，避免从 PATH 选中伪造的 sandbox-exec。策略包含文件系统、网络、平台只读默认项和需要的系统服务规则。
这是 macOS 专用后端，非 macOS 选择 Seatbelt 会产生明确不可用错误。

参见 seatbelt.rs:61、manager.rs:437。

Windows。 配置可选择 unelevated、elevated 和 MXC；不能把三者描述成完全相同的安全能力。传统 RestrictedToken 的 unelevated 路径支持有限的写限制，但源码明确拒绝无法强制的 split read/deny-read 规则和不兼容写根集合。

参见 windows_sandbox.rs:134、sandboxing/windows.rs:15、sandboxing/windows.rs:122、manager.rs:530。

10.8 远程执行：控制器决定策略，executor 落地隔离

Environment 暴露统一的 ExecBackend、ExecutorFileSystem 和 HTTP client。
本地环境提供本机实现，远端环境通过 exec-server 通信；命令运行、补丁文件操作和能力发现都据此绑定到所选环境。在远端情况下，Core 不把控制器机器的 sandbox wrapper 套到一个网络请求上冒充隔离，而是携带 URI-native 权限意图，由 executor 本机执行沙箱准备。

参见 environment.rs:1178、process_manager.rs:1303。

exec-server 在实际启动边界把 PathUri 转成本机路径、物化 workspace roots、检查 helper 路径和沙箱能力，再调用相同的 SandboxManager。如果请求带 sandbox context 而 executor 无法选择有效后端，会返回 sandbox intent cannot be enforced on this executor。
因此 Core 中“本机 SandboxType::None”在 executor-managed 分支可以表示本机不负责安装沙箱，并不自动意味着远端裸跑。
反过来，如果请求本身没有 sandbox context，exec-server 也存在明确的无沙箱启动路径。

参见 process_sandbox.rs:174、process_sandbox.rs:247。

10.9 网络与凭据也是执行上下文的一部分

网络策略可由托管代理执行，目标 host/protocol/port 构成网络审批对象。运行时在本地准备代理环境，在远端准备 network proxy launch config；阻止网络的决定可以取消正在运行的进程。
某些显式提权路径会绕过托管代理，所以终端权限快照必须保存启动时是否绕过网络限制，不能只看后续 turn 的代理设置。

参见 network_approval.rs:1、unified_exec.rs:276、process_manager.rs:429。

Shell snapshot、环境变量继承和 credential broker 共同影响子进程看见的环境。凭据 masking 有能力检查与降级告警，源码中存在因受保护 snapshot 不可用而恢复未遮蔽凭据继续运行的路径。
因此不能把“启用网络代理”写成“所有 shell、所有远端场景都绝不会看见凭据”的保证。
这里需要分别核对执行 shell、snapshot 是否成功、代理与 broker 是否有效，以及具体失败模式。

参见 unified_exec.rs:524、process_sandbox.rs:49。

10.10 阅读与验证这部分代码时应保留的边界

现有测试覆盖工具并行、生命周期、统一执行、stdin 审批、Guardian retry、Code Mode 与不同沙箱政策等场景。可从 core/tests/suite/tool_parallelism.rs、unified_exec_stdin_approval.rs、guardian_sandbox_retry.rs 和 core/src/tools/sandboxing_tests.rs 继续追踪预期行为。
这些测试文件是源码中的设计证据；本文的代码阅读不等于已在当前 Windows 主机运行全套测试，更不等于跨平台沙箱认证。

对于一次真实工具调用，应按“当前 tool plan → 具体请求与环境 → execpolicy/补丁评估 → reviewer 决策 → 实际后端 → 退出与副作用”逐层定位。这样才能把模型判断、框架策略、用户授权和操作系统强制限制分开，并准确描述一次失败究竟发生在哪一层。

11. Skills、插件、MCP 与 Hooks

11.1 四种扩展分别解决什么问题

这四者经常同时出现，但承担不同职责：

  • Skill 是模型可阅读的任务说明与配套资源，主要扩展“怎样做”。
  • Plugin 是能力包、来源与安装管理单位，可以带 Skill、MCP 配置和 Hooks。
  • MCP 是外部工具和资源的连接、发现与调用协议，主要扩展“能访问什么”。
  • Hook 是宿主生命周期上的回调，可以观察、修改或阻断特定阶段。

Skill 不等于可执行权限；安装 Plugin 不等于它的全部工具已被允许；发现 MCP server 不等于每个工具都对模型可见；列出 Hook 不等于它已经可信并会执行。

这个分层对应源码中的不同 crate：ext/skills、core-plugins、codex-mcp 和 hooks，核心再通过 extension contributor 和具体工具适配器把它们接入模型循环。

源码：Skills extension、PluginsManager 配置、McpBinding、Hooks registry。

11.2 Skills 使用目录摘要与按需正文

Skills extension 通过多个 provider 构造 catalog，来源可以包括 host、bundled、executor 和 cloud。host 的发现输入结合工作目录、config layer stack 和插件 skill snapshots；主执行环境的仓库发现，不直接等同于宿主本地 cwd。

模型最初通常获得 Skill 名称、描述和入口位置，而非每个 Skill 的全部正文。目录渲染有 metadata budget，正文注入有独立截断限制，避免技能数量一多就吞掉模型窗口。

用户显式提到技能时，collect_explicit_skill_mentions 从已准备好的 catalog 解析目标，再调用对应 provider 读取 main prompt，将其转换成 SkillInstructions。

对于非普通路径资源，正文片段还携带 authority、package、main resource 访问说明，模型可以通过 skill tools 继续读取配套资源，而不必把远程资源伪装成本地文件路径。

框架还记录显式或隐式调用的遥测以及插件归属，但这不表示它能保证模型会遵循 Skill 的每句话；技能正文最终仍是模型上下文中的指令材料。

源码：host discovery 输入、目录渲染、显式选择与正文注入、SkillInstructions 构造。

11.3 Skills 的时序与门控

thread start 保存 provider 和配置相关状态，step preparation 准备稳定的 catalog，world state 或 turn input 再负责渲染。这样，执行环境还未就绪时与就绪之后，目录变化可以通过正式的状态更新进入模型历史。

catalog 是否提示、是否包含 bundled skills、是否跳过 host discovery、是否使用 executor discovery V2，都有独立配置或 feature。SkipHostSkillDiscovery 默认关闭；executor capability discovery 两代标志也都不是默认全开。

代码还存在 shadow selection experiment，它用于运行独立的候选选择实验，并不能推断默认产品已经把技能选择完全交给另一个 Agent。

源码：thread start、thread context 门控、step preparation、discovery features。

11.4 Plugin 的载入结果是能力投影

PluginsManager 处理 marketplace、安装包、manifest、启用状态、远端 catalog、本地缓存及插件能力。调用方输入 PluginsConfigInput，其中包括配置层、插件开关、provider、远端能力和 product SKU 等上下文。

core 获取 plugin load outcome 后，再剔除当前 turn 禁用的插件。剩余结果分别提供 skill roots/snapshots、MCP server 配置、hook sources、提示词说明等。

这比“插件直接运行任意代码”更准确：manifest 中声明的不同能力，经由各自子系统接入，并继续接受该子系统的准入和策略检查。

推荐插件又是另一条门控链。基础 Plugins 默认开启，但 RecommendedPlugins 默认关闭；是否渲染推荐列表，还依赖配置、认证和推荐能力。远端插件和分享等也有独立 feature。

源码：PluginsConfigInput、初始上下文中的插件选择、插件相关默认值、推荐门控。

11.5 MCP runtime 与 binding 的分工

McpRuntime 可以刷新 server、认证与目录；McpBinding 则保存一次 step 使用的不可变视图，包括连接、client、配置、工具目录和 prepared calls。

binding 的 tools() 返回冻结的 model-visible catalog；prepare_call() 绑定到准确的 client 和 metadata，并再次检查工具是否对模型可见。资源读写同样经由 binding 的 client/connection 集合执行。

core 的 MCP runtime projection 负责把当前配置、环境、权限、禁用插件等投影为期望状态，再发布到 runtime。cwd、工作区、approval policy、reviewer、permission profile 或 Windows sandbox 变化，都会参与是否需要刷新的判断。

MCP 连接还可能具有不同的执行环境 owner。工具执行和资源访问不能只凭一个字符串 server name 选择本地进程或网络连接，需要保留环境归属。

源码：McpBinding 的冻结目录、prepare_call 可见性检查、runtime 投影、刷新输入比较。

11.6 从 MCP 工具目录到原生工具调用

McpHandlerCache 把 MCP ToolInfo 归一化为 harness 的 tool schema 和执行 handler，并使用共享定义缓存减少同一大 schema 的重复解析。

接入时要经过工具可见性、Apps policy、搜索/延迟暴露等规则。部分 agent plugin MCP schema 还有字节预算，避免一个插件声明特别大的工具说明淹没整个 prompt。

模型调用最终由 McpHandler 转交 handle_mcp_tool_call，继续进入 MCP 调用的审批、执行、结果转换和归属记录流程。因此 MCP 是工具运行时的一类后端，而不是另一条可以跳过 harness 生命周期的旁路。

传统工具名可以采用 mcp__server__tool 前缀；命名、namespace 和 deferred catalog 的实际形态受配置及模型能力影响。阅读日志或开发新工具时，不应把某一种命名方式写成所有部署的固定约定。

源码：MCP schema 缓存、接入工具 registry、McpHandler、MCP 调用实现。

11.7 Hooks 是真正会影响控制流的扩展点

当前 hook runtime 覆盖 SessionStart、SubagentStart、UserPromptSubmit、PreToolUse、PermissionRequest、PostToolUse、Stop、SessionEnd、Interrupt、PreCompact、PostCompact 和模型请求等阶段。

不同事件的结果不同：

  • PreToolUse 可以继续、更新输入，或阻断调用。
  • PermissionRequest 可以参与权限请求的处理。
  • 多种生命周期事件可以附加上下文或要求停止。
  • 异步 Hook 的结果会在后续安全时机 drain，而不是任意时刻修改模型历史。

Hook 结果经 HookAdditionalContext 形成正式的上下文片段，started/completed 事件则进入用户事件和遥测通道。这样可以同时追踪“Hook 执行了什么”以及“它给模型加入了什么”。

源码：hook runtime、PreToolUse、异步结果 drain、上下文注入。

11.8 Hooks 的信任与配置不是可忽略细节

CodexHooks 当前默认开启，但实际执行还要求存在匹配的 handler、handler 启用，且满足信任条件。配置层、插件 hook source、内容 hash 和 managed/builtin 状态都参与发现。

列表模式可以显示尚未 trusted 或被禁用的 Hook；执行模式则会跳过不满足条件的项目。插件内容变化可能导致已有信任不再匹配，避免更新包后静默沿用旧授权。

PluginHooks 这个旧 feature 已标记 Removed。当前 build_hooks_config 从启用插件结果获取 hook sources，并把总 CodexHooks 开关传给 registry，不能把旧标志当作插件 Hook 的唯一开关。

bypass_hook_trust 是明确配置项，不应因为默认 Hooks 可用，就假设信任检查被绕过。工具 Hook 也需要携带调用所属环境，不能在错误的本地 cwd 执行远程项目回调。

源码：HooksConfig 构建、列表与执行配置、信任判断、执行准入。

12. 多 Agent、目标与长期记忆

12.1 多 Agent 是线程运行时，不只是并行请求

Codex 的 Agent 有自己的 thread、状态、模型上下文、任务路径、输入和执行生命周期。父子关系由 SessionSource::SubAgent 等结构记录，控制面负责 spawn、消息投递、等待、恢复、interrupt 与执行容量。

当前同时保留 V1 和 V2。Collab 对应 multi_agent，默认开启；MultiAgentV2 对应 multi_agent_v2，默认关闭。实际版本还受配置与模型能力选择影响，不能把 V2 handler 的存在写成所有 Codex 会话的默认工具集。

V1 以传统 Agent ID 控制接口为主；V2 使用 task path、消息与可恢复运行时，并提供 spawn_agent、send_message、followup_task、interrupt_agent、list_agents 和 wait_agent 等不同职责的工具。

源码：多 Agent 默认值、V1 工具 namespace、V2 handlers、版本选择。

12.2 V2 spawn 调用链

spawn_agent handler 先解析参数和 fork mode，再调用共享 thread_spawn::spawn。共享准备层负责校验消息、构造 child config、生成规范任务路径与 SessionSource，最后调用配置好的 Agent backend。

任务路径由父路径拼接 task name，避免调用方任意伪造完整层级。spawn 返回的是已接受的 Agent 和配置快照，不能等同于“子任务已经完成”。

backend 独立负责子线程寿命，工具 handler 负责把结果转换为模型可见的输出、活动事件和遥测。这种分层允许不同宿主使用同一套准备规则，而不重复实现配置继承。

源码：V2 spawn handler、共享 spawn、AgentControl spawn。

12.3 子 Agent 继承的是受控快照

child config 从父 step 的有效模型和设置开始，叠加请求的 model/reasoning、role、service tier，然后再次应用运行时 cwd、approval policy 和 permission profile，避免从过期 config clone 出错误权限。

具体 override 是否暴露给模型由 tool spec 与配置决定。V2 的描述明确要求默认继承模型；但是底层准备实现仍有独立校验，不能把自然语言提示中的约束误写成 Rust 类型系统已强制拒绝所有 override。

fork mode 的 all 使用完整历史继承路径，none 新建上下文。V2 解析器还接受旧的正整数格式，但将其解释为 FullHistory，不再按数字限制继承 turn 数。

FullHistory 也不是机械复制每个 item。实现会过滤 reasoning、普通工具调用与输出、特定 Agent 通信等内容，重新处理角色说明、提示和 baseline；子线程不会继承父线程累计 usage。

源码：child config 准备、运行时权限覆盖、fork_turns 解析、历史保留过滤。

12.4 调度、消息与资源限制

线程数量、同时执行数量与生成深度是不同的约束。配置含 agent_max_threads、agent_max_depth 和 V2 的 max_concurrent_threads_per_session；运行时执行 limiter 通过计数和 guard 维护活动容量。

消息投递也区分 QueueOnly 和 TriggerTurn：普通消息排入目标 Agent 的输入，后续任务可以唤醒空闲 Agent。通信数据保留 author、recipient、任务路径和是否触发 turn，避免失去来源。

wait_agent 处理状态通知，interrupt_agent 停止当前 turn，followup_task 则投递后续任务。它们不必与“关闭线程”混为一谈；停止一次执行不代表删除线程状态。

主动协作模式同样不是全局硬编码。V2 会根据配置、模型消息和 reasoning effort 生成提示：没有显式覆盖时，Ultra 可以选择 proactive 提示，其他情况通常使用 explicit-request-only；宿主仍可配置自定义文本。

源码：执行容量 limiter、消息的 wake mode、配置上限、协作模式推导。

12.5 Goals 把“继续做”变成显式状态机

Goal extension 接入 thread、turn、tool lifecycle 和 token usage，使用数据库中的 goal 记录与运行时 accounting 共同控制持续执行。

目标状态包括 active、paused、blocked、usage_limited、budget_limited、complete。默认 goals feature 开启，但工具可用还要求持久线程状态，review 子 Agent 也会被排除。

创建目标后，线程进入 idle 时，continue_if_idle 读取当前目标、检查 deferral 和状态，再通过 start_turn_if_idle 注入 continuation steering。它不会无条件向已经忙碌的线程再发一个普通用户 turn。

目标变更与 continuation 启动之间持有同一个 goal-state permit，避免用户刚修改或清除目标，旧 continuation 却越过检查启动。token 和 usage accounting 则决定预算限制及停止原因。

这也说明 goal 与普通任务描述的差别：普通对话文本本身不会自动等价为持久目标；目标工具、状态迁移、预算和自动继续，需要由明确的宿主协议驱动。

源码：Goal extension 注册和可用性、状态枚举、idle continuation、Goals 默认值。

12.6 长期记忆的读写路径分离

长期记忆不等于模型权重更新，也不等于把全部旧聊天永久放进 prompt。它是持久化摘要、索引、使用记录与检索入口组成的外部上下文系统。

ext/memories 负责读取侧的上下文注入和专用工具；memories/read 负责 citation 解析和 read-usage 分类；memories/write 负责后台提取、全局整合及文件产物维护。

读取注入要求 MemoryTool feature 与 memories.use_memories 同时满足；专用 list/search/read/note 工具另需 dedicated_tools。V1/V2 使用各自 namespace，配置变化时会固定线程已选择的版本，保持初始摘要和检索工具一致。

V2 说明被切成有界片段，每个片段使用 UTF-8 字符边界和字节上限；这不等于整个 memory summary 只允许一个片段的大小。

源码：Memory extension 配置、注入与分片、专用工具门控、read crate 职责。

12.7 后台提取与全局整合

记忆写入管线在 eligible root thread 启动时异步运行。ephemeral 会话、未开启 memory feature、非 root Agent 会直接跳过；没有 state DB 或额度条件不满足也不执行模型提取。

第一阶段按线程提取：从数据库领取有租约的有限批作业，筛选适合总结的 rollout 内容，调用模型生成 raw memory、rollout summary 和可选 slug，处理敏感信息后写回 stage-1 输出。年龄窗口、空闲时间、扫描数量、并发和重试控制限制了后台工作量。

第二阶段持有全局 lease，挑选有界的 stage-1 输入，同步 raw_memories.md 和 rollout_summaries/，清理失效输入与过期扩展资源，并生成相对上次成功 baseline 的工作区 diff。

只有文件工作区发生变化，才启动 consolidation 子 Agent，把低层提取结果整合成 MEMORY.md、memory_summary.md 和可复用技能等。成功后更新 baseline 与消费记录；这不是每次用户发消息就从零总结所有历史。

如果选择 V1 且开启 dual write，启动器会为 V1 和 V2 各执行一条管线；这属于显式配置，不能推断所有用户都在双写。

源码：启动条件与双写、Phase 1、Phase 2、数据库记忆作业。

12.8 记忆 Agent 的权限与证据边界

consolidation Agent 会关闭记忆生成与使用、Apps、Plugins、collab 和技能 MCP 依赖安装，清空 MCP servers，并设置 AskForApproval::Never，避免自动整合再次递归调用全套扩展。

通常它只获得本地 memory root 写权限且不联网。但实现明确保留父级选择的 PermissionProfile::External；这类情况下，隔离由外部执行环境负责，不能把“始终由 Codex sandbox 强制断网”写成无条件保证。

记忆 feature 在当前提交的默认值是 false。读、写行为还分别受 use_memories、generate_memories 和线程 memory mode 等影响，用户环境中已出现 memory 提示词，不能用来反推开源默认值。

记忆产物是从历史生成的二级证据。好的上层指令仍需要要求模型区分历史记录与当前事实、查询具体出处，并对可能变化的信息重新验证；citation parser 可以追踪引用，不能替代来源准确性判断。

还要注意仓库 README 的路径说明落后于代码：其“orchestration 仍位于 core/src/memories”描述已不符合当前目录。本文以上述 memories/write/src 的真实调用链为准。

源码：consolidation 配置限制、External profile 例外、记忆默认关闭、citation 解析。

13. 前端呈现与 SDK：同一个执行内核的不同客户端

13.1 TUI 的三层职责

终端界面主要可以沿以下结构阅读：

  1. Tui 处理终端模式、输入事件、帧调度和绘制。
  2. App 协调 app-server、当前会话、历史加载、审批、重连与输入所有权。
  3. ChatWidget / HistoryCell / BottomPane 表现消息流、工具活动、输入框与交互面板。

App::run 的事件循环同时处理终端输入、应用内部事件以及后端事件。后端采样和命令执行不应阻塞绘制线程；工具完成、审批到达、用户输入等通过事件驱动 UI 状态变化。

源码：TuiEvent 与 Tui、主运行循环、多路事件选择、后端事件消费。

13.2 流式文本并非收到一个 token 就重画全部历史

HistoryCell 是界面中的显示单位，既能表示已提交历史，也能暂时表示仍在变化的活动项。转录视图可以缓存活动尾部，但需要通过 revision/cache key 使变化正确失效。

streaming::StreamState 负责按换行推进 Markdown 收集，并维护已提交渲染行的 FIFO。controller 决定何时形成显示项，chunking 根据队列压力计算排空节奏，commit_tick 落实提交。代码围栏和表格还有专门的流式处理。

这解释了为什么“模型流式返回正常”并不直接等于“终端每种宽度下都显示正确”：协议增量、Markdown 结构、显示行队列和终端帧是不同层。渲染缺陷应在相应层定位。

源码：HistoryCell 的显示与缓存语义、流式管线与 FIFO 约束、流式控制器。

13.3 输入框为什么需要状态机

ChatComposer 不只是字符串编辑器，还要协调补全弹窗、文件/插件/skill 提及、原子化文本元素、粘贴以及提交。输入框的一次 Enter 可能代表提交，也可能是粘贴文本中的换行。

尤其在部分 Windows 终端中，粘贴会以快速连续的字符、Enter 和 Tab 事件出现。PasteBurst 通过纯状态机识别这种输入，返回缓冲或刷新决策，再由调用方修改编辑框。这能避免把粘贴中的换行误识别为提前提交任务。

这类状态处理属于客户端职责。它最终仍要把正确的 UserInput 发给服务端，而不是改变模型主循环。

源码：ChatComposer 的输入契约、PasteBurst 状态机。

13.4 exec 输出是协议的再次投影

EventProcessor 接收 typed app-server 通知，再由人类可读处理器或 JSONL 处理器产生输出。JSONL 处理器维护 item ID 映射、运行中的待办列表、usage、最终消息和错误等状态。

因此 codex exec --json 的输出不能直接当作原始 Responses API 流，也不能假设它与 app-server 通知逐字相同。它是为命令行消费定义的一层事件契约。

14.1 配置不仅是读取一个 config.toml

  2. core::config::ConfigBuilder 将合并的 TOML 转成运行配置，结合 harness overrides、工作目录及受管要求落实约束。

14.4 Provider 信息与 Provider 运行对象

ModelProviderInfo 是可配置、可序列化的后端描述，包含连接、认证与重试等信息。ModelProvider trait 则是运行时抽象，承接后端相关的请求认证、目录能力、账户状态及恢复等行为。

models-manager 管理可用模型及其元信息，包含打包目录、静态目录和远程刷新/缓存等路径。模型信息会影响上下文窗口、推理设置和能力选择，不能只把模型 ID 当作一个最终拼到 URL 的字符串。

替换 provider 也不等于所有能力自动一致。例如远程压缩、WebSocket、模型目录发现及认证恢复都可能有后端能力条件。

源码：ModelProviderInfo、ModelProvider trait、ModelsManager trait、内置模型目录加载。

14.5 认证状态由专门的管理层持有

CodexAuth 不止 API key 一种形式，还建模 ChatGPT 登录、外部 token、headers、Agent Identity、个人访问 token 和部分云后端认证。AuthManager 管理共享认证状态，支持刷新及“仅当认证仍未变化时刷新”等并发保护路径。

应区分以下三个方向：

  1. 客户端连接 app-server 的认证：保护集成通道。
  2. harness 访问模型后端的认证：决定模型请求的身份和可访问服务。
  3. MCP/插件访问外部服务的认证：属于另外的连接与授权域。

它们可以在产品中关联，但不是一个 token 在所有方向通用。账户切换、workspace routing 或 provider 改动也可能影响目录缓存和请求路由。

源码：CodexAuth、AuthManager、有条件 token 刷新、provider workspace routing。

14.6 Token、上下文预算、缓存与实际费用

TokenUsage 分别记录输入、缓存输入、输出、推理输出和总量；TokenUsageInfo 保留累计用量与最近一次请求用量。Session 还有区分 Sampling 与 SpendingOnly 的记账路径：某个后台请求即使没有成为当前上下文窗口，也可能已经产生实际用量。

因此至少要分清四个问题：模型窗口中当前有多少内容、本轮累计用了多少 token、哪些输入命中了缓存，以及服务端按什么账户规则结算。前两者参与压缩、目标预算和界面统计；缓存计数及 prompt_cache_key 不等于可以离线准确算出费用。本文没有根据源码中的默认模型名或 token 数推算当前价格。

prompt_cache_key 由请求层按策略生成；WebSocket continuation 则检查前缀并用 previous_response_id 传递增量。它们与本地持久化历史、压缩窗口又是不同机制，排查性能或费用时不能合并成一个“缓存开关”。

源码：TokenUsage / TokenUsageInfo、两类 usage 上下文、用量更新、缓存键策略、请求中的缓存键。

15.2 为什么可以在中途继续补充要求

用户追加输入进入服务端与内核的输入协调机制。它可能用于 steer 当前任务，也可能根据当前状态启动下一轮。新的输入与设置在合适边界被采纳，已开始的工具副作用不能通过修改聊天文本自动撤销。

同理，中断要处理采样、待执行任务、正在运行的工具、事件和最终状态。只关闭前端窗口与完整取消 turn 的语义并不完全一致。

实现细节见第 4～5 章；外部操作类型见 turn/steer 和 turn/interrupt。

15.3 远程执行、Worktree 与进程身份分别解决什么

这几个模块容易被“远程 Agent”一词混在一起：

  • 远程 app-server：客户端与运行时分处不同位置。
  • exec-server / environment manager：运行时将工具和文件操作送往选定执行环境。
  • WorktreeManager：管理 Git checkout 的创建、归属和移除，帮助不同任务分离代码工作目录。
  • runtime-agent-instance：源码声明的职责是临时运行身份注册与请求断言，属于认证基础设施。

这四种边界可以组合，也可以独立存在。独立 thread 本身不等于独立 worktree；独立 worktree 也不等于独立操作系统沙箱。远程连接成功不自动证明它访问的代码就是当前用户终端中的那份 checkout。

源码：TUI 后端目标、环境选择与接入、WorktreeManager、runtime 身份模块。

15.4 图片与实时语音是额外的输入输出管线

图片进入上下文前有准备过程，涉及模型能力、detail、大小处理、附件引用和失败替代文本。不能把图片当成一段普通文本历史。

实时会话还有独立的启动、音频输入、文本输入、handoff、输出和关闭生命周期。realtime_conversation 将实时流与后端工作连接；具体传输、功能开关及模型能力要另外确认。它不是用“不断重复普通 turn/start”就能完整描述的接口。

源码：图片准备、实时会话启动、实时音频输入、实时外部协议。

16.1 这个系统需要测试哪些契约

Codex 的测试并不限于“模型是否答对”。大量重要行为可以使用固定模型事件和模拟执行环境验证：

  • 请求携带了哪些指令、工具和历史，工具结果是否与调用匹配。
  • 断流、重试、认证恢复和取消后，是否产生正确状态与事件。
  • 压缩后历史能否继续使用，resume/fork 是否保留正确分支语义。
  • 审批拒绝、沙箱限制、网络审批等是否阻止对应行为。
  • TUI 是否正确显示增量、宽度变化、审批和历史分页。

16.2 日志、trace 与状态文件不是同一种证据

排障时可以按问题选择证据：

  • 界面显示错误：看 TUI 事件处理、HistoryCell、渲染 snapshot。
  • 模型请求错误：看实际组装的请求、provider、传输及重试事件。
  • 工具未执行或被拒绝：看路由、策略、审批决定及执行环境错误。

17.3 从实现中可以提炼的设计原则

以下是本文基于源码提出的工程归纳，不是项目官方承诺：

第一，复用服务契约降低多前端分叉。 TUI、exec 和外部集成共享 app-server 语义，进程内模式继续复用处理器，减少一套界面成功、另一套界面失效的独立执行路径。

第二，采用 typed 生命周期而非只拼接聊天字符串。 thread、turn、step、item、operation、event 各有职责，使 steering、审批、恢复和工具反馈有明确关联。

第三，上下文是受预算约束的工作状态。 指令、WorldState、历史、工具目录和压缩共同决定模型看到什么；磁盘中保存的全部事件不等于每次请求都原样发送。

第四，安全通过多层约束落实。 工具 schema、策略、审批、受管要求和 OS 隔离解决不同问题。模型理解一条规则与系统强制执行这条规则不能画等号。

第五，可恢复性依赖持久化和重放契约。 在事件流、索引、历史投影以及压缩边界上保持一致，比简单把终端输出写入文本文件复杂得多。

第六，扩展能力仍需生命周期。 Skills、MCP、Hooks、多 Agent 和长期目标都要参与上下文、工具暴露、状态和取消流程，不能只增加一个入口而不处理其余边界。

17.4 附录：概念解释

  • Harness：围绕模型运行的控制与执行系统，包含上下文、循环、工具、状态和边界。
  • Thread：可持续、可恢复的工作会话；不自动意味着独立 Git checkout。
  • Turn：一轮工作生命周期；通常包含多次模型采样和工具执行。
  • Step：一次采样准备与请求对应的执行粒度，拥有本步所需的一致视图。
  • Item：消息、调用或活动的结构化内容单位；客户端投影与模型内容类型须区分。
  • WorldState：按章节组织的运行环境和相关上下文状态，参与初始/差量上下文生成。
  • ToolSpec：模型可见工具定义；有定义不代表已获执行授权。
  • ToolExecutor：工具执行公共契约；具体执行还需运行时与环境。
  • Approval：对请求操作的审批决定；不等于 OS 隔离实现。
  • Sandbox：在实际执行后端施加文件、网络等访问限制的机制。
  • Compaction：将长历史变成可继续工作的受预算上下文，不等于删除全部磁盘记录。
  • Rollout：会话过程的持久化记录之一；与 UI、模型历史和 SQLite 索引用途不同。
  • Skill：带说明及资源的能力包；通过发现、选择和指令注入参与工作。
  • MCP：外部工具和资源的协议接入边界，与本地 shell 执行环境不同。
  • Hook：特定生命周期的扩展回调，具体回调点决定它能改变什么。
  • Goal：持久目标及其续跑状态；不应简单理解为一个无限 while 循环。
