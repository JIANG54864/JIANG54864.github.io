1. 总览

最鲜明的设计是 “Everything is a Plugin”：模型适配器、工具注册表、会话服务、默认 Agent Loop、Web 界面都通过 Cordis 插件装配。应用启动时选择一组配置，形成具体的运行系统。

可以把主要职责分成六类：

  • 应用装配：CLI、Profile、Bundle 与配置覆盖。
  • Agent 驱动：输入队列、轮次状态、模型请求与继续执行。
  • 能力执行：文件、Shell、Web、MCP、浏览器等服务及工具。
  • 状态管理：会话事件、持久化、恢复和面向不同消费者的投影。
  • 上下文管理：提示词、工作区指令、Skill、附件和摘要压缩。
  • 交互与控制：Web/Desktop/SDK、审批、用户提问和权限设置。

2. 源码目录与整体结构

这里的 core/ 是公开服务与默认实现的聚集处；其名称不代表其中的实现不能替换。比如 core/agent 定义公开 Agent 服务，core/agent-loop 提供默认驱动，两者有明确区分。包组说明（packages/README.zh.md）、默认工厂注册（packages/core/agent-loop/src/index.ts:329）。

3. Cordis：一切皆插件如何落地

3.1 Context、Service 与依赖注入

Cordis 为插件提供共享上下文 ctx。服务以稳定的名字出现在上下文中，例如：

插件通过 inject 声明需要的服务。依赖满足后，插件才激活，所以 YAML 中“谁写在前面”不能简单等同于运行时的启动先后。比如 DeepSeek API Key 提供方声明依赖 llm，再将路由注册到 LLM 服务。提供方入口（packages/llm/llm-deepseek-api-key/src/index.ts:16）、Cordis 依赖注入实现（vendor/cordis/src/registry.ts:300）。

3.2 事件是行为扩展点

插件通过类型化事件观察或拦截流程。这里需要区分两类经常同时出现的事件：

  • 持久 Session 事件：如 user/message、tool/result、turn/end，表示已经发生、需要保留的事实。
  • 实时扩展事件：如 agent/pre-step、llm/stream、tools/pre-execute，用于当前进程内的执行与策略协调。

部分扩展事件采用 waterfall，也就是环绕式中间件：监听器调用 next()，才继续执行下一层；直接返回则短路后续流程。它可以实现策略拒绝、替代返回或围绕原有行为增加逻辑。源码还防止同一监听器重复调用 next()。waterfall 实现（vendor/cordis/src/events.ts:236）。

因此，增加一个执行策略通常可以注册监听器完成；无需把策略条件写进默认循环的每个分支。

3.3 注册同时承担生命周期管理

工具、适配器和监听器的注册会绑定 Cordis effect。卸载插件时，effect 撤销注册并清理资源。例如 registerAdapter() 在 effect 内发布路由，释放时删除其拥有的路由；工具 executor 也有相应的撤销逻辑。适配器注册（packages/llm/llm/src/index.ts:394）、工具 executor 注册（packages/core/tools/src/index.ts:325）。

这使热重载不仅涉及重新读取配置，还涉及旧能力何时停止提供服务、正在运行的 Agent 何时释放资源。声明依赖和清理 effect 是插件实现的一部分。

3.4 能力接口、实现和模型工具分开

项目用 capability seam 表达一项可替换能力的三个角色：

  1. Service Definition：声明调用接口与行为要求。
  2. Service Provider：实现本地、远程或其他执行方式。
  3. Consumer：使用服务，常见形式是面向模型的工具。

以文件能力为例，模型工具处理参数和工具输出，文件服务提供操作接口，fs-sandbox 在写操作前检查允许写入的位置。替换提供方时，可以保留上层工具的使用方式。能力说明（docs/architecture.md）、文件限制实现（packages/fs/fs-sandbox/src/index.ts:156）。

4. 启动：Profile、Bundle 与配置叠加

4.1 三种“预设”分别控制什么

源码中有三个容易混淆的概念：

  • Profile 决定启动哪种应用组合，如 Web、Headless 或 SDK，保存在 Harness home 中。
  • Agent Preset 决定某个 Agent 使用的插件能力集合，通过带 scope 的插件树和会话绑定管理。
  • Permission Preset 把沙箱模式与审批策略组合成用户可选择的权限模式。

它们分别属于应用启动、Agent 能力选择和执行权限三个层次。Agent Preset 还管理具体插件版本的存活：新定义可以激活新一代组合，仍有 Agent 使用的旧组合继续保留，直到引用释放。Agent Preset 注册与版本管理（packages/preset/agent-preset-registry/src/index.ts:93）、权限预设（packages/interaction/permission-presets/src/index.ts:59）。

4.2 官方 Profile 的组合

Bundle 是可分发的代码和 Cordis patch；Profile 按顺序堆叠 Bundle，再叠加用户配置。当前官方模板为：

base 提供共享的模型、Agent、工具、会话、权限等能力。web-app 增加 Web 产品，headless 增加一次性任务运行器，sdk-app 增加 JSON-RPC 服务。sdk-minimal 独立声明自己的最小插件树，不叠加 base。官方模板定义（packages/util/official-bundles/src/bundles.ts:10）、最小 SDK 组合（packages/bundle/sdk-minimal/cordis.patch.yml:1）。

5. Agent Loop：一条请求如何执行

5.1 公开 Agent 服务与默认驱动

core/agent 提供公开的 Agent 接口与注册表；core/agent-loop 将自己注册为工厂，负责创建和驱动 Agent。具体驱动类叫 ReactLoopAgent，这里的名称指 ReAct 式模型与工具循环，与前端 React 组件没有关系。工厂发布（packages/core/agent-loop/src/index.ts:329）、驱动类（packages/core/agent-loop/src/agent.ts:112）。

阅读时先建立两个概念：

  • Step：一次模型请求及其触发的工具执行；请求失败后可能在同一 step 内重试。
  • Turn：一次输入处理轮次，可以包含多个 step；如果前置策略拒绝输入，也可以没有任何模型 step。

例如“读取文件，再根据结果改文件，再解释修改”，可能在一个 turn 内依次完成多个模型请求。不能把一个 turn 直接等同于一次 API 调用。

5.3 为什么先准备调用，再提交用户输入

prepareCall() 会绑定实际适配器与模型能力。默认循环在这一阶段完成后，才提交本次进入模型上下文的 system/user 消息。因此，准备阶段发生取消时，不会把尚未真正接受的输入提前记成已进入模型上下文。准备与输入提交顺序（packages/core/agent-loop/src/agent.ts:435）。

同一 step 的模型选择和工具集合在准备时固定。重试复用该 step 的组装结果，不重复执行 pre-step，也不重复追加同一条用户消息。旧的 agent/request 钩子不能随意替换已选定的 provider、model 或 reasoning effort；这些选择应在 step 准备前通过公开模型选择接口完成。重试分支（packages/core/agent-loop/src/agent.ts:542）、选择校验（packages/core/agent-loop/src/agent.ts:630）。

5.4 实时输出与最终消息分开

模型流的实时增量通过进程内 agent/assistant-stream 事件交给界面。流结束后，完整的紧凑流记录随 assistant/message 或日志专用的 assistant/attempt 结算持久化。失败、重试和流错误等尝试因此可以被记录，而不必全部加入后续模型历史。流读取与结算（packages/core/agent-loop/src/agent.ts:480）。

这意味着“界面刚显示了一段文字”与“这次流已经形成持久记录”存在时间差；进程在结算前突然退出，不能保证最后显示的所有增量都已保留。

6. 工具系统：注册、策略、并发与 PTC

6.1 注册与可见性

工具系统集中管理工具定义、参数 schema、执行函数和输出处理。每个 step 先解析一次满足条件、在当前 Agent scope 可见的工具集合，再把这份集合交给 Prompt 和 executor 使用，保持“模型得到的声明”与“该步准入的能力”一致。工具注册（packages/core/tools/src/index.ts:128）、工具集合解析（packages/core/tools/src/index.ts:257）。

全局工具和 Agent scope 中的工具可以按作用域解析。作用域限制与 step 准入同时约束声明和执行查找；单纯在展示层省略 schema，不能替代执行策略、guard 与能力提供方检查。

6.2 一次工具调用的受控流水线

共享流水线主要经过：

6.3 并发工具有顺序与屏障

多个工具调用会按 parallel-safe 或 exclusive 分类。可并行调用进入有上限的调度池；exclusive 调用形成执行屏障。策略准备和提交保持相应顺序，允许重叠的是可并行的 dispatch/body 阶段；返回结果仍对应原始调用顺序。批次调度（packages/core/tools/src/batch.ts:76）、执行与提交（packages/core/tools/src/batch.ts:187）。

默认循环的 maxParallelToolCalls 为 10，是可配置的批次并发控制。PTC 内部另有 maxParallelSubCalls，两者控制不同层次。循环默认值（packages/core/agent-loop/src/constants.ts:6）、PTC 子调用配置（packages/core/tool-executor-ptc/src/config.ts:6）。

6.4 Native executor

Native 模式向模型公布每个可见工具的 JSON schema。模型直接返回对应工具名与参数，再由 executor 交给共享批次调度器。其实现很薄，重点是声明与调度之间的连接。NativeToolExecutor（packages/core/tool-executor-native/src/index.ts:8）。

6.5 PTC：用程序组织工具调用

PTC 指程序化工具调用。其模型协议只暴露 run_code，普通工具以程序 SDK 形式提供，例如 await tools.some_tool(args)。模型可以在一段程序里做循环、筛选、计算和多次工具调用，再把选定结果返回给模型循环。PTC executor（packages/core/tool-executor-ptc/src/index.ts:12）。

这种方式改变的是调用表达与中间结果处理位置。例如，查询多份资料后先在程序中筛选匹配项，可以减少每份中间数据都进入下一次模型请求的需要。源码体现了这种设计意图，但不能据此断言具体节省多少 token 或提高多少成功率。

PTC 仍遵守工具执行控制：

  • 程序只能绑定该 Agent 当前准入的工具；内层调用继续经过共享流水线和 guards。
  • 工具子调用记录专门的 PTC dispatch 事件，外层结果再汇总为模型可见输出。
  • SDK 声明支持多种语言的表达；本仓库 Node runtime 提供方实际运行 TypeScript，声明的隔离方式为 process。
  • 运行状态是否保留取决于配置，不能笼统认为每次都重开环境，或变量一定永久保留。

内层派发（packages/core/tool-executor-ptc/src/ptc.ts:648）、子调用记录（packages/core/tool-executor-ptc/src/ptc.ts:550）、Node 提供方（packages/ptc-runtime/ptc-runtime-node/src/index.ts:19）、持久性配置（packages/ptc-runtime/ptc-runtime-node/src/config.ts:10）。

本地 base 配置默认启用 native executor，PTC executor 默认禁用；选择 PTC 需要相应配置，而不是所有会话天然进入代码模式。默认组合（packages/bundle/base/cordis.patch.yml:496）。

6.6 MCP 工具也接入同一个注册表

MCP client 插件连接外部服务，将其工具注册为 mcp__<serverName>__<rawName>。配置支持 stdio 和 Streamable HTTP；一个插件实例对应一个服务，卸载时断开连接、撤销工具和命名空间。因此 MCP 工具进入统一工具系统，而不要求在 Agent Loop 中增加专门的协议分支。MCP client（packages/mcp/mcp-client/src/index.ts:1）。

7. 模型接入：统一调用与提供方适配

7.1 LlmRuntime 管路由，Adapter 管协议

ctx.llm 管理 provider 路由、模型元数据和统一流式调用。具体适配器负责把 Harness 消息转换成提供方请求，并把提供方响应转换成通用 StreamChunk。重复占用同一路由会失败，路由注册也绑定插件生命周期。适配器抽象（packages/llm/llm/src/index.ts:203）、路由注册（packages/llm/llm/src/index.ts:394）。

当前组合既包含 DeepSeek 提供方，也挂载 pi-ai 多提供方适配器。后者是否产生可用路由取决于用户配置，不能把“插件已安装”直接理解为“所有模型均已配置好”。base 中的适配器配置（packages/bundle/base/cordis.patch.yml:131）。

7.2 prepareCall 固定一次请求的配置

LlmRuntime.prepareCall() 捕获适配器注册、模型能力、重试策略和具体请求控制，并返回只能派发一次的调用对象。派发时还会检查配置是否匹配，避免热更新期间把旧的能力判断与新的适配器实现混用。prepareCall 实现（packages/llm/llm/src/index.ts:960）。

默认循环据此判断该模型是否支持历史中的系统提示词更新、工具更新等能力，再决定怎样记录与投影请求。不能假定所有提供方采用完全一样的系统消息更新方式。

7.3 这份快照的 DeepSeek 适配器使用 Messages

llm-deepseek 提供共享传输，API Key 和账号插件分别提供鉴权、发现和路由注册。API Key 路由的凭据由 credentials 服务或启动环境解析，传输层接收已经形成的鉴权请求头。API Key provider（packages/llm/llm-deepseek-api-key/src/index.ts:33）。

这里值得注意的是，这份实现直接调用 Messages 接口：构造 /v1/messages 请求，通过 SSE 读取响应，再经过解析和翻译得到 Harness 的统一流。它不能被简单描述成一个 OpenAI Chat Completions 调用封装。端点规则（packages/llm/llm-deepseek/src/messages-api.ts:9）、HTTP 请求与响应翻译（packages/llm/llm-deepseek/src/adapter.ts:142）。

图片和文件输入还涉及持久附件引用、上传复用、请求尺寸与字节预算，以及失败时的内联处理。这些是模型适配层和附件服务的职责，Agent Loop 仍使用统一消息类型。请求准备（packages/llm/llm-deepseek/src/adapter.ts:89）、适配器说明（packages/llm/llm-deepseek/README.zh.md）。

7.4 重试由恢复扩展点承担

llm-retry 监听 agent/request-error，读取提供方声明的重试策略，结合错误码、重试次数和退避时间决定是否继续。安排重试时先记录相应会话事件，等待过程支持取消。恢复策略（packages/llm/llm-retry/src/index.ts:190）、重试事件（packages/llm/llm-retry/src/index.ts:184）。

因此，提供方失败、重试策略和主循环推进有各自的归属，扩展提供方时不必直接修改循环里的每一种网络错误分支。

8. Session：事件日志、持久化与恢复

8.1 日志是事实，模型历史是投影

Session 的核心是 append-only 事件日志。Session.append() 为数据创建可 JSON 序列化的快照，分配序号和时间戳、冻结后提交；先把事件加入日志，再广播给观察者。append 实现（packages/core/session/src/index.ts:806）、提交点（packages/core/session/src/index.ts:892）。

日志中包含消息、工具结果、轮次状态、权限变化、压缩等事实，其中只有部分内容参与模型历史。deriveMessages() 沿当前 surface 中的节点派生请求消息。因此有三份需要分清的数据：

  1. 原始事件日志：保留可恢复事实。
  2. 当前模型历史：由日志和 surface 操作派生。
  3. 面向界面或业务的状态投影：例如当前权限、轮次状态或会话列表信息。

模型历史派生（packages/core/session/src/index.ts:981）。

“模型可见就必须有日志依据”是这套架构的重要约束。它允许根据会话记录重建输入；这不意味着日志中的每个事件都会交给模型，也不保证再次请求模型会得到完全相同的输出。

8.2 内存提交与可靠落盘分开

持久化接口与 JSONL 提供方分离。JSONL 后端默认采用带校验和的 Zstandard 编码；只有选择 compression: none 时，文件才是可直接阅读的纯文本 JSONL。编码配置（packages/session/session-persistence-jsonl/src/index.ts:94）。

批次写入后执行 fsync；写入或同步失败会尝试回滚到先前字节长度，避免重试造成重复序号。写入与同步（packages/session/session-persistence-jsonl/src/index.ts:1413）。

检查点策略在模型派发前、顶层工具执行前和下一步准备时 flush 会话。flush 失败会阻止相应模型或工具调用。比起“每次 append 都已落盘”，更准确的理解是：内存日志提交与持久化有不同的提交时点，关键外部动作前设置持久化检查点。检查点策略（packages/session/session-checkpoint-policy/src/index.ts:20）。

8.3 恢复先取得写句柄，再重建 Agent

先取得写句柄用于排除同一会话的并发恢复。持久化层处理文件格式和有效日志，Agent 层处理缺失的工具结果、step/end 与 turn/end。恢复实现（packages/core/agent-loop/src/index.ts:763）。

存储层还负责读取支持的历史格式并迁移到当前逻辑格式。当前版本状态及代际文件规则以仓库文档为准；不能把“能迁移旧格式”理解为能够任意降级读写。会话格式状态（docs/session-format-status.md）、格式与恢复总览（docs/architecture.md）。

flowchart LR
    E[追加 Session 事件] --> S[当前 Surface]
    S --> M[deriveMessages]
    E --> P[检查点与持久化]
    P --> J[压缩或纯文本 JSONL]
    J --> R[取得写句柄并读取]
    R --> C[补齐中断轮次收尾]
    C --> A[重建 Agent]

8.4 取消和恢复不等于回滚外部效果

取消时，已开始的工具需要完成清理；未派发调用可以获得合成的中止结果。执行失败时，循环也会补齐缺失结果，使日志中的工具调用关系能够收尾。批次中止处理（packages/core/tools/src/batch.ts:225）、step 故障收尾（packages/core/agent-loop/src/agent.ts:363）。

但文件写入、命令和外部 API 可能已经产生效果。重建会话只能恢复已记录事实和继续运行所需的上下文，不能保证恢复原来的 shell 进程，也不能自动撤销此前执行的动作。PTC 同样明确要求检查中断前可能已完成的效果，不会自动重放整段程序。PTC 中断约定（packages/core/tool-executor-ptc/src/ptc.ts:123）。

9. 上下文：提示词、指令、Skill 与压缩

9.1 System Prompt 由多种贡献组装

SystemPrompt 提供 section、context、tool、variable 等注册方式，汇总全局和 Agent scope 的贡献。scope 中的同名贡献可以覆盖更远层的贡献，组装后还存在相应的 waterfall 扩展点。注册入口（packages/core/system-prompt/src/index.ts:436）、assemble 实现（packages/core/system-prompt/src/index.ts:621）。

动态 runtime context 与系统提示词有独立处理方式，最终可以作为带来源的持久 user-role 快照进入历史。上下文既包含 system message，也包含指令、时间、工具结果、附件等普通历史节点；不能只在一个固定 system 字符串里寻找全部信息。runtime context 投影与消息构造（packages/core/agent-loop/src/runtime-context.ts:119）。

9.2 工作区指令按使用过程更新

agent-instructions 提供兼容 AGENTS.md 的指令加载。首次请求前提供基线指令；文件工具成功触达相关路径后，处理嵌套目录以及指令文件修改、移除等情况。消息通过 agent/pre-step 加入，并携带来源。插件职责（packages/context/agent-instructions/src/index.ts:1）、输入插入与文件触达（packages/context/agent-instructions/src/index.ts:330）。

时间上下文同样由独立插件生成，可按配置刷新。时间上下文（packages/context/time-context/src/index.ts:51）。

9.3 Skill 目录与全文分开

tool-skill 提供持久的会话 Skill 目录以及 skill 工具。模型主动使用 Skill 时，通常先看到名称和描述，确定需要使用后再加载完整说明；调用时仍检查该 Skill 是否存在以及是否允许模型调用。Skill 工具定义与加载（packages/skill/tool-skill/src/index.ts:85）。

用户也可以在消息首行用 /<skill-name> 显式调用允许用户调用的 Skill。这条路径由 pre-step 加载并注入全文，不必等待模型自行选择。显式调用处理（packages/skill/tool-skill/src/index.ts:181）。

这属于上下文按需加载机制。Skill 是指导 Agent 工作的内容，工具是执行能力；加载说明不会自动替代工具服务，也不会自行授予更大的执行权限。

9.4 压缩替换可见历史，原始日志保留

压缩接口与具体摘要策略分离。compaction-basic 在 pre-step 根据 token 压力尝试压缩，也可在 context-window-exceeded 错误时尝试压缩恢复；它并不处理所有模型失败。自动触发（packages/compaction/compaction-basic/src/index.ts:157）、容量错误恢复（packages/compaction/compaction-basic/src/index.ts:213）。

一次压缩大致经过：选择安全范围、记录开始、生成摘要、确认范围没有被并发改变，再提交替换。提交时追加摘要事件和携带 surfaceOp: replace 的摘要消息，使后续模型历史使用新的摘要节点。压缩事务过程（packages/compaction/compaction-basic/src/region.ts:173）、摘要提交（packages/compaction/compaction-basic/src/region.ts:470）。

被摘要遮蔽的旧事件仍在日志中；工具调用和结果还必须成对处理，压缩范围不能随意切开未完成的交互。工具配对约束（packages/compaction/compaction/src/tool-pairing.ts）。

因此，“保留原始事件”与“模型仍能看到所有原文”是两件事。摘要会产生额外模型调用，也可能遗漏细节；压缩解决的是容量管理和可追溯的历史替换，无法提供无损的无限上下文。

图：压缩事务如何改写模型视图

压缩提交的是新的摘要事件及 surface 替换操作，不是物理删除旧事件。摘要生成期间若选中范围或相应 surface 已发生不兼容变化，稳定性校验会阻止安装过时摘要。

10. Subagent：委派、Spawn 与 Fork

10.1 子代理有服务与生命周期

Subagent 服务根据 provider 启动本地或外部后端，并检查深度、提供方能力、父 Agent 身份等条件。并发数和深度上限可配置，不能将源码默认值当成永久产品限制。准入与后端选择（packages/subagent/subagent/src/index.ts:271）。

本地可继续委派会创建子会话身份、可继续的运行描述，以及父子结果投递关系，还会捕获委派时的模型选择和权限覆盖。它比一次普通异步函数调用多了持久身份和后续交互管理。本地子代理创建（packages/subagent/subagent/src/manager.ts:379）。

外部后端提供执行句柄，在需要向父会话投递时记录 external 目录项，不要求存在本地可继续 Session。不能把本地子会话的恢复能力直接套到所有 provider 上。外部启动（packages/subagent/subagent/src/manager.ts:483）、external 目录记录（packages/subagent/subagent/src/catalog.ts:150）。

10.2 Spawn：新的上下文

subagent-spawn-in-process 在同一 Cordis 运行环境中创建新 Agent，使用独立 Session 与系统提示，默认不复制父会话历史，并可选择独立 Agent Preset。它适合把一个边界清楚的子任务连同必要说明交给新的上下文。Spawn 实现（packages/subagent/subagent-spawn-in-process/src/index.ts:1）。

10.3 Fork：继承已完成前缀

subagent-fork-in-process 捕获父日志截至最近一次 turn/end 的已平衡完成前缀，排除父 Agent 正在执行的工具轮次。捕获发生在创建时，这份前缀随后成为子会话自己的持久历史；恢复子会话时不会重新复制父 Agent 后来新增的内容。Fork 说明与捕获（packages/subagent/subagent-fork-in-process/src/index.ts:1）、创建路径（packages/subagent/subagent-fork-in-process/src/index.ts:77）。

Spawn/Fork 描述的是上下文与会话构造方式。这里的 in-process 后端不会因为“创建了子代理”就自动建立操作系统隔离环境；实际工具权限仍由能力提供方与执行策略控制。

图：Spawn、Fork 与外部后端的边界

Spawn/Fork 的区别主要在子会话初始上下文。Fork 只在创建时捕获父会话最近一个已完成 turn 的平衡前缀，恢复子会话不会重新复制父方的新历史；外部 provider 的句柄也不必对应本地可恢复 Session。

11. Web、Desktop 与 SDK 如何复用运行时

11.1 Web：后端服务加客户端插件

Web profile 在共享 base 之上装入 Web 服务、客户端模块和连接插件。默认服务地址为 127.0.0.1:3080；本机启动会打开浏览器，--no-open 可以关闭自动打开行为。Web 服务配置（packages/bundle/web-app/cordis.patch.yml:175）。

浏览器入口很薄，主要创建并执行 AppWebEntry，具体界面能力由客户端插件提供。Node 端负责发现客户端模块和提供启动资料，连接层连接网关与浏览器 fetch/SSE 客户端。浏览器入口（apps/web/src/main.ts:1）、客户端装配（packages/bundle/web-app/cordis.patch.yml:223）。

Desktop 使用 Electron，启动独立的 Desktop Host。Host 调用共享 runProfile()，使用桌面保留的 desktop profile；其默认端口为 0，由操作系统分配。Host 子进程（apps/desktop/src/host-process.ts:209）、Desktop Host 入口（apps/desktop-host/src/index.ts:33）。

desktop 由桌面产品管理，不应把它当成普通 npm CLI 的第六个官方模板。桌面架构说明（docs/architecture.md）。

11.3 SDK：通过进程外协议驱动同一引擎

TypeScript SDK 解析同版本 dsh，默认启动 --profile sdk 子进程，通过 stdio JSON-RPC 驱动 Agent。它提供客户端 API，Agent Loop 仍运行在服务进程中。CLI 版本与启动解析（packages/sdk/client/src/launch.ts:56）、子进程启动（packages/sdk/client/src/client.ts:223）、SDK 服务配置（packages/bundle/sdk-app/cordis.patch.yml:14）。

Python SDK 同样使用 stdio JSON-RPC，并定位配套打包运行时；默认要求显式提供 dsh_home 或非空 DSH_HOME。Profile 和 patch 仍决定服务端的应用组成。Python 客户端（python/sdk/src/deepseek_harness/client.py:589）。

Headless 是一次性任务载体，SDK 是程序控制载体，ACP 则提供自动化协议服务。它们共享相同的能力装配思路，具体行为由各自 Profile 决定。

12. 权限与沙箱的实际职责

12.1 文件效果策略与审批分别控制什么

沙箱服务中的文件效果模式为：

  • read-only：限制写效果，仅允许必要的特殊输出等。
  • workspace-write：允许工作区、显式额外写入目录及后端定义的临时区域。
  • danger-full-access：绕开这层文件 confinement。

该服务面向与宿主共享内核和文件系统的子进程。网络和进程可见性不属于这三个模式表达的文件策略，不能从名称推导出网络隔离保证。模式定义（packages/sandbox/sandbox/src/index.ts:1）。

审批策略则是：

  • ask：需要审批时委派已配置的应答方；没有可用应答方时不放行。
  • never：不发起询问，对需要审批的请求直接拒绝。

never 本身不是“自动批准”。danger-full-access + never 之所以具有广泛访问能力，是因为前一个沙箱设置已绕开文件限制。审批语义（packages/interaction/user-approval/src/index.ts:59）、拒绝逻辑（packages/interaction/user-approval/src/index.ts:296）。

12.2 默认值要看最终组合

底层 sandbox-policy 类的缺省模式是 read-only，而随产品交付的 base patch 默认采用 workspace-write + ask，还允许 DSH_PERMISSION_MODE 覆盖。文档或调试时必须查看最终 Profile，不能只看某个类的默认字段。服务默认值（packages/sandbox/sandbox-policy/src/index.ts:137）、产品组合（packages/bundle/base/cordis.patch.yml:243）。

Permission Preset 负责把这两个独立设置组合并记录到会话。执行服务继续读取自己的设置；切换预设不代表执行逻辑都集中到了预设服务里。权限写入与投影（packages/interaction/permission-presets/README.zh.md）。

12.3 进程限制与文件 API 限制都存在

本地进程后端按平台选择 Linux bubblewrap/Landlock、macOS Seatbelt 或 Windows ACL restricted-token。Windows 后端明确声明为 partial enforcement，不能据此宣称各平台都有完全相同的隔离强度。平台选择与限制（packages/sandbox/sandbox-local/src/index.ts:1）。

文件 API 还由 fs-sandbox 在写入前检查：read-only 直接拒绝；workspace-write 重新解析目标路径，再判断是否落在允许写入的目录中，以避免一直使用此前解析的旧目标。文件写入检查（packages/fs/fs-sandbox/src/index.ts:156）。

这些控制面向通过相应能力执行的操作。Cordis 插件和 YAML 中的 !!js 配置属于可信应用代码范围，不能把“工具有沙箱”扩展成“任意第三方插件也被隔离”。仓库安全说明明确指出该开发者预览尚未经过安全审计。Loader 配置语义（docs/cordis-primer.zh.md）、项目安全说明（SAFETY.zh.md）。

13. 这套设计值得关注的地方

  • 组合是一级机制：应用由具名 Profile 和可覆盖 Bundle 构成。同一能力可以用于不同载体，代价是理解当前行为时必须追踪最终配置。
  • 状态围绕日志组织：模型历史、业务投影、持久化与恢复都有事件依据。新增模型可见输入时，需要同时考虑它如何记录和重建。
  • 执行策略集中到公共路径：Native、PTC 和 MCP 都复用工具注册与执行控制，有助于减少每种调用方式各写一份策略的重复。
  • 生命周期是插件接口的一部分：注册可撤销，Agent 要取消、等待执行收尾、清理 scope 和持久句柄。热更新能力背后有真实的资源管理成本。
  • 上下文优化需要保持语义一致：提示词更新、工具声明、压缩、Fork 和模型重试都不能只考虑 token 数，还需要维持可重建历史和工具调用配对。
